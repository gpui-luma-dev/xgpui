# GPUI 1.28.1 public API ledger

Running ledger for [issue #284](https://github.com/gpui-luma-dev/xgpui/issues/284).
Each work package adds the public API changes it introduces to non-extension
crates, including re-exports and changes reached through re-exported helper
crates. Every entry needs the user's individual review before release. Approving
the implementation does not approve the API.

Review outcome is one of: pending, approved, changed, rejected.

## 02 — Dependency foundation

### `gpui::http_client` loses the GitHub helpers and `anyhow` re-exports

- **Change:** `xgpui` re-exports the whole helper crate (`pub extern crate http_client;`
  in `gpui.rs`). `http-client-gpui-unofficial` 1.28.1 removes:
  - `http_client::github` (GitHub release lookup helpers, native only);
  - `http_client::github_download` and the `github-download` feature;
  - the `pub use anyhow::{Result, anyhow}` re-export.
  So `gpui::http_client::github`, `gpui::http_client::github_download`,
  `gpui::http_client::Result` and `gpui::http_client::anyhow` no longer exist.
- **Origin:** upstream removed these from the shared HTTP crate (Zed moved them elsewhere).
- **Source compatibility:** breaking for any downstream code that names those
  paths, or that enables `http-client-gpui-unofficial/github-download` itself.
  No XGPUI crate, extension or app uses them.
- **Serialization/string formats:** none identified. Wire behavior of the
  remaining HTTP types is unchanged.
- **Migration:** depend on `anyhow` directly; use a GitHub client of your choice
  instead of `http_client::github`.
- **Could live in an extension:** not applicable. This is a removal in a pinned
  helper crate. Keeping the old items would mean forking `http-client` instead of
  using the published helper identity.
- **Versioning:** a removal reachable from `xgpui`'s public API, so it counts
  toward the `xgpui` version proposal in package 12.
- **Review outcome:** pending.

### `gpui::SchedulerLocalExecutor::to_send` and `scheduler::SendLocalExecutor`

- **Change:** `xgpui` re-exports `scheduler::LocalExecutor` as
  `gpui::SchedulerLocalExecutor`. Scheduler 1.28.1 adds
  `LocalExecutor::to_send(&self) -> SendLocalExecutor` and the
  `SendLocalExecutor` type, which spawns `Send` futures from any thread onto the
  executor's dispatch thread. `SendLocalExecutor` itself is not re-exported by
  `xgpui` yet; package 10 builds `gpui::SendForegroundExecutor` on it.
- **Origin:** upstream, for the web foreground executor.
- **Source compatibility:** additive.
- **Serialization/string formats:** none identified.
- **Migration:** none.
- **Could live in an extension:** no. It belongs to the shared scheduler helper.
- **Review outcome:** pending (review together with package 10's foreground API).

## 04 — Text layout

No public signatures change (`LineWrapper::is_word_char` → `break_indices` is
`pub(crate)`). Visible behavior does change and needs review with screenshots:

- **Wrapping:** line breaks follow ICU/UAX #14 line-break segments with grapheme
  awareness. Breaks no longer split shaped clusters, and RTL runs wrap by segment.
  Line counts can change for CJK, RTL, hyphenated and punctuated text.
- **CoreText:** the first run keeps its exact point size, and the ligature-breaking
  size nudge only alternates on runs that insert text. Single-run widths now match
  AppKit; text after empty runs no longer shifts.
- **DirectWrite:** tabs produce invisible glyphs with their layout advance, so carets
  and hit testing land on tab stops instead of collapsing tabs to zero width.
- **Serialization/string formats:** none identified.
- **Review outcome:** pending.

## 03 — Core cache, ownership and diagnostics

Ported from Zed #66293 (arena in `Rc`), #65951 (cached views and inherited
opacity), #66358 (borrow and window diagnostics) and #65952 (subscriptions kept
for reused cached views). `EntityMap` and its access-scope methods are
`pub(crate)`, so they are not public API.

### `AppCell::try_borrow_mut` returns `anyhow::Result<AppRefMut>`

- **Change:** was `Result<AppRefMut<'_>, std::cell::BorrowMutError>`. The error now
  carries the attempted borrow location and the location of the existing borrow
  group. `AppCell` is `#[doc(hidden)]`.
- **Source compatibility:** breaking only for code that names `BorrowMutError` in a
  match or a type annotation. `.is_ok()`, `.is_err()`, `?` into `anyhow` and
  `.unwrap()` keep working.
- **Serialization/string formats:** the panic and error text for double borrows
  changes (it now names locations). No persisted format is affected.
- **Migration:** treat the error as `anyhow::Error`.
- **Could live in an extension:** no. It is the app cell itself.
- **Review outcome:** pending.

### `#[track_caller]` on `AppContext::update_window` and window-update wrappers

- **Change:** caller locations propagate through window updates, so window-operation
  errors and panics point at application code. `log_err` sites in upstream's
  `window.rs` paths gain operation and window context. XGPUI-specific sites keep
  their existing messages.
- **Source compatibility:** non-breaking for callers and implementors.
- **Serialization/string formats:** log and error text change only.
- **Review outcome:** pending.

### Behavior

- **Element arena:** now held in its own `Rc` allocation, so draws reaching it through
  the raw arena pointer no longer alias a live `&mut App` (removes undefined behavior).
  No API change.
- **Cached views:** cache reuse is invalidated when inherited opacity changes (compared
  by bits, so NaN still reuses). This sits next to XGPUI's glyph-brush and layer-capture
  cache keys. `div` applies element opacity around its paint callback.
- **Subscriptions:** entities read by reused cached and deferred content keep their
  observers across frames. Nested access scopes stop inner reads from leaking into
  outer views, and released entities are not restored.

## 05 — Core frame pacing

Ported from Zed #66237 (frame limits and pacing) and #66281 (configurable power and
thermal intervals).

### `WindowOptions::low_power_frame_interval` and `thermal_frame_interval`

- **Change:** two new public `Option<Duration>` fields beside `inactive_frame_interval`.
  Defaults are `Some(33.3 ms)` and `Some(16.7 ms)`, the limits 1.27.0 already
  hard-coded, so default behavior is unchanged. `None` disables a limit. The longest
  applicable interval wins.
- **Source compatibility:** breaking for exhaustive `WindowOptions { .. }` literals
  that don't use `..Default::default()`. Confirmed in-repo: gamut-lab's
  `tests/compatibility.rs` lists every field and needed the two new ones.
- **Serialization/string formats:** none identified (`WindowOptions` is not serialized).
- **Migration:** add `..Default::default()`, or set the two fields.
- **Could live in an extension:** no. Frame limiting is in the core window frame loop.
- **Review outcome:** pending.

### Behavior: pacing kept, upstream's notify throttling not adopted

- **Adopted:** a `FramePacer` keeps throttled frames on a steady cadence, corrects small
  dispatch delays up to a quarter interval without catch-up bursts, and restarts after
  larger stalls. Display-link ticks with no frame demand neither use up a slot nor wake
  the platform. Mandatory presentations bypass limits.
- **Not adopted (conflict policy):** upstream 1.28.1 also applies the limits to redraws
  requested only with `cx.notify()` and to high-rate-input presentations. XGPUI documents
  (#211, `WindowOptions`) that notify-driven redraws are not throttled, and recommends
  that engine surfaces present new frames through `EngineSurface::on_present` + `notify`.
  Taking upstream's rule would cap those presentations at about 30 fps in unfocused
  windows and in Low Power Mode. XGPUI keeps limits on animation-frame demand only (next-frame
  callbacks and forced renders). `test_notify_redraw_bypasses_inactive_throttle`
  guards this rule.

## 10 — Web and send-capable foreground execution

### `gpui::SendForegroundExecutor` and `ForegroundExecutor::to_send`

- **Change:** new `pub struct SendForegroundExecutor` (`Clone`, `Send`) with
  `spawn<R: Send + 'static>(&self, future: impl Future<Output = R> + Send + 'static) -> Task<R>`
  (`#[track_caller]`), and `ForegroundExecutor::to_send(&self) -> SendForegroundExecutor`.
  A worker thread can submit a `Send` future that is polled on the main thread.
- **Origin:** upstream (Zed), wrapping scheduler's `SendLocalExecutor` from package 02.
- **Source compatibility:** additive.
- **Serialization/string formats:** none identified.
- **Migration:** none. Replaces ad hoc "post a closure to the main thread" paths.
- **Could live in an extension:** no. It is a core executor primitive that
  `xgpui-web`'s Fetch client depends on, and it needs scheduler internals.
- **Review outcome:** pending.

### `gpui_web::FetchHttpClient::new` / `with_user_agent` become public and take a `SendForegroundExecutor`

- **Change:** previously `pub(crate) fn new(Arc<WebDispatcher>)` and
  `pub(crate) fn with_user_agent(Arc<WebDispatcher>, &str)`. Now
  `pub fn new(SendForegroundExecutor) -> Self` and
  `pub fn with_user_agent(SendForegroundExecutor, &str) -> anyhow::Result<Self>`.
  Requests are started through the foreground executor instead of the removed
  web-dispatcher function queue (`MainThreadItem::Function`,
  `dispatch_function_on_main_thread`, both crate-private).
- **Origin:** upstream.
- **Source compatibility:** additive for downstream code: the constructors were
  private, and `WebPlatform::fetch_http_client()` / `fetch_http_client_with_user_agent()`
  keep their signatures. Configured credentials and user agent are unchanged.
- **Serialization/string formats:** none identified (same Fetch request construction).
- **Migration:** none.
- **Could live in an extension:** no. It is the web backend's HTTP client.
- **Review outcome:** pending.

### Not adopted: upstream's `gpui_platform.rs` web constructors

Upstream 1.28.1 stops attaching a Fetch HTTP client in `gpui_platform::application()`
(on Wasm), `application_with_web_backend()` and `single_threaded_web()`. It also
rewrites `current_platform` with `cfg_select!` and drops the OpenHarmony arm. XGPUI
keeps its version (conflict policy: our code wins). Taking it would silently leave
web apps without `cx.http_client()`, breaking URL images and requests for any app
relying on the default. `cfg_select!` would also raise the toolchain needed, for a
cosmetic change. `WebPlatform::new(true)` already selects the `Auto` backend, so
there is no behavior to gain.

## 07 — Anchoring and platform API

Ported from Zed #66496 (`Anchored::attach`), #55800 (standalone modifier timeout),
#66283 (macOS Spanish-ISO key equivalents) and the core part of #53746 (corner-radius
hook and `Pixels::to_i32`; that commit's Wayland part belongs to package 08). All are
additive. No serialization or string format changes were identified.

### `Anchored::attach(target: Bounds<Pixels>, corner: Anchor) -> Self`

- **Change:** places the element's anchor corner on a corner of `target` and flips to the
  other side of `target` (with the offset) when that side fits better. `SwitchAnchor` fit
  mode has no effect with `attach`. `position` is unchanged.
- **Could live in an extension:** no. It is part of the core `Anchored` element and its
  window-edge fitting.
- **Review outcome:** pending.

### `Pixels::to_i32(self) -> i32`

- **Change:** truncates toward zero; out-of-range values saturate and NaN becomes zero.
- **Could live in an extension:** possible, but it is a geometry conversion used by core
  and backends.
- **Review outcome:** pending.

### `Keystroke::is_modifier_key(&self) -> bool`

- **Change:** whether the key itself is a modifier. Used so a pending single-modifier
  sequence (for example the first `shift` of `shift shift`) is flushed after the normal
  timeout instead of staying pending.
- **Review outcome:** pending.

### `Window::set_client_corner_radii(&mut self, Corners<Pixels>)` and `PlatformWindow::set_client_corner_radii`

- **Change:** apps that draw their own rounded window corners can tell the platform, so
  platform effects (Wayland blur and rounded input regions, package 08) match. The trait
  method defaults to a no-op, so other platforms and existing `PlatformWindow`
  implementors are unaffected.
- **Source compatibility:** additive, including for out-of-tree `PlatformWindow` implementors.
- **Could live in an extension:** no. It reaches the platform window.
- **Review outcome:** pending.

### Behavior

- **Modifier sequences:** a standalone modifier sequence that doesn't complete is now
  flushed after the timeout, so the next shortcut works.
- **macOS Spanish-ISO:** shortcut key equivalents are corrected.
- **Pasteboard:** upstream makes `Pasteboard::general` / `find` return `Option`. XGPUI
  already keeps an optional native pasteboard inside `Pasteboard` and handles `nil` the
  same way, so it was left as it is.

## 08 — Wayland

Ported from Zed #64058 (activation requests) and the Wayland part of #53746
(background effects and client regions). The changed Wayland types are internal to
`xgpui-linux`, so there is no public API change. `Window::set_client_corner_radii`
(package 07) now has a Wayland implementation.

### Behavior

- **Activation:** each `xdg_activation` token carries its own pending window, URI or
  path action, so concurrent requests no longer overwrite each other (that used to leave
  GNOME's launch indicator until timeout). Requests use the latest real keyboard or pointer
  press and its surface. Without one, window activation still asks for a token so the
  compositor can show the window wants attention, and URI/path opens keep the tokenless
  fallback. Startup now issues an activation request.
- **Blur:** `WindowBackgroundAppearance::Blurred` uses `ext-background-effect-v1` when the
  compositor offers it (niri, newer KDE), and otherwise the deprecated KDE blur. GNOME offers
  neither, so there is no blur there, as before.
- **Opaque region:** set only for opaque, server-decorated windows. Client decorations keep
  transparent shadows and antialiased corners.
- **Corner radii:** the blur and input regions follow the radii an app sets with
  `set_client_corner_radii`. No XGPUI app or extension sets them yet (xgpui-shell could, as
  a separate change).
- **Kept from XGPUI:** the #271 frame-loop diagnostics (the configure trace now runs before
  `update_window`) and the #119 GPU-recovery imports and paths.
