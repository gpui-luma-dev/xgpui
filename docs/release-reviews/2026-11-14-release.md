Why: Cargo keeps semver-incompatible `xgpui` versions side by side, so with compatible-looking bumps `cargo update` in a core-3 app could pull, for example, `xgpui-svg` 0.3.5 or `xgpui-windows` 2.2.1, whose core-4 types fail to type-check against the app. This follows the 1.26.2 release (majors for backends, pre-1.0 minors for extensions), not the core 3.0 release.
`xgpui-ios` leaves its upstream-aligned 1.26.x numbering: it returns `Rc<dyn gpui::Platform>`, and semver requires a major.
All candidate versions were confirmed unpublished on crates.io before applying them.

Applied to: every package manifest and internal requirement (`Cargo.toml`), `scripts/release-packages.json`, `Cargo.lock` (`daily refresh-locks`: 14 internal version lines, no external changes; `daily check-locks` passed), the accounting table, the What's-new version table, iOS version text in its README and pages, and `pages/releasing.html` family text.
Packaged README install snippets that still named `xgpui` 2.0.0, `xgpui-platform` 2.0.0 or older extension versions now name the candidates (core, Apple, Linux, macOS, platform, web, Windows, gamut, media, shader, svg). The `xgpui-macros` and `xgpui-color` READMEs keep stale snippets because editing them would change their unchanged packages.
