Shader options

XGPUI gives you several ways to put pixels on screen, from GPUI's built-in primitives to your own GPU engine. They all draw into the same window and keep GPUI's ordering, clipping and opacity. Start with the simplest option that does the job and move down the list only when you need more.

GPUI primitives

Core GPUI, no extension. Quads (with corner radii, borders and the built-in linear gradient, slash and checkerboard backgrounds), shadows, paths, underlines, glyph and image sprites, and platform surfaces.

  • Use for: almost all application UI. Styling a div() produces these.
  • Why it's special: it's the fastest path and always available. The renderer batches primitives by kind with fixed, tuned shaders on Metal, DirectX and wgpu, so there is nothing to compile, validate or manage.
  • Limits: a fixed set of looks. Anything beyond them needs one of the options below.

GPUI quads

Core GPUI, no extension. Draw directly in a canvas() element's paint callback with window.paint_quad(…), using fill(bounds, background), outline(bounds, color, style) or quad(…) for corner radii, borders and border styles, plus window.paint_path for vector shapes.

canvas(|_, _, _| {}, |bounds, _, window, _| {
    window.paint_quad(fill(bounds, rgb(0x202830)));
    for (i, value) in values.iter().enumerate() {
        let bar = bounds_for(bounds, i, *value);
        window.paint_quad(quad(bar, px(3.), rgb(0x4aa3ff), px(0.), rgb(0x000000), BorderStyle::Solid));
    }
})
  • Use for: custom drawing that doesn't fit an element tree: charts, timelines, grids, meters, editors' gutters and selections.
  • Why it's special: you get the speed of GPUI primitives with immediate-mode control. Quads go through the same batched, tuned renderer as styled elements, with GPUI's clipping, opacity and pixel snapping, and there is no shader to write.
  • Limits: the built-in quad and path looks only, and each quad is recorded on the CPU every frame it's painted.

CPU rasterization (tiny-skia)

Core GPUI SVG, xgpui-svg and xgpui-parley. Vector content is rasterized on the CPU with tiny-skia (through resvg for SVG), then drawn from the sprite atlas like any image.

  • Use for: SVG icons and illustrations, full-color SVG documents with progressive preview and detail, and Parley text rasterization (including the browser font lab).
  • Why it's special: exact, deterministic output that looks the same on every backend, and no GPU code to write. xgpui-svg adds shared scheduling and image-memory accounting so large documents don't stall the UI.
  • Limits: costs CPU time and atlas memory, and redraws at a new size need a new raster.

Brushes

xgpui-shader, Brush. Solid, linear and elliptical radial fills, procedural noise, freeform and regular mesh fields and distorted Hermite patches, applied to painted backgrounds, borders, text glyphs and vector fills and strokes.

  • Use for: rich fills on ordinary elements: gradient cards and borders, gradient text, noise texture, mesh backgrounds.
  • Why it's special: brushes draw in the main render pass with no intermediate color texture, no mask texture and no extra render-pass boundary. They cost about the same as a quad, scale perfectly and work on Metal, D3D11 and wgpu.
  • Limits: a fixed set of brush kinds. For your own shading, use shader paints or instanced shaders.

Guide: Main-pass brushes · brush gallery ↗

Paints

xgpui-shader, Paint. SolidColor, Gradient and MeshGradient render into a cached offscreen texture through GPUI's custom-draw path, then fill backgrounds and paths with bg_paint and paint_path_with_paint.

  • Use for: expensive fills you want to compute once and reuse, above all Hermite mesh gradients built with GPU compute.
  • Why it's special: output is cached and reused until its inputs or size change, so heavy work isn't repeated every frame. Native producers run on Metal and D3D11, with a wgpu path elsewhere, and need no app-side OS branches.
  • Limits: each paint uses an offscreen texture; for many small, changing effects, brushes or instanced shaders are cheaper.

Shader paints

xgpui-shader, shader_paint, feature portable-shaders. Write one WGSL function, fn paint(input: PaintInput) -> vec4<f32>, and drive it from Rust with named ShaderParameters (up to 32 f32 scalars and vectors).

  • Use for: custom procedural fills (patterns, animated fields, generative backgrounds) on styled elements, borders and paths.
  • Why it's special: you write portable WGSL once; it's validated and translated to MSL, HLSL and SPIR-V for each backend. Parameters are reflected from the source, so there's no manual buffer layout, and output is cached like any paint.
  • Limits: a deliberately safe subset: no loops, no discard, no textures, resource bindings or compute.

Guide: Shader paints · Shader paints vs instanced shaders

Instanced shaders

xgpui-shader, instanced, feature portable-shaders. Typed WGSL fragment shaders, fn shade(input: ShaderInput, parameters: Parameters), drawn directly in the main render pass with one small, typed instance record per draw.

  • Use for: many repeated effects in scene order: particles, glows, rounded and custom shapes, configurable gradient shadows, soft animated borders. The spatial canvas grid draws this way.
  • Why it's special: consecutive compatible instances batch into one draw while keeping exact scene order, so thousands of effects stay cheap; the regression suite renders 5,000 instances in a single run. It's the widest-reaching option: Metal, D3D11, wgpu, browser WebGPU and WebGL2. Programs can opt into linear Display P3 output on wide-gamut windows.
  • Limits: instance records are up to 128 bytes of f32 scalars and vectors; no textures, resource bindings or compute.

Guide: Instanced shaders · shader playground ↗

Layer effects

xgpui-shader, LayerEffect and BackdropBlur. Capture a finished subtree, then apply group opacity, blur, saturation, grayscale, brightness, contrast, inversion or destination blend modes; or blur what is behind an element.

  • Use for: frosted-glass panels, dimmed or desaturated disabled regions, blend-mode compositions, true group opacity.
  • Why it's special: effects apply to whatever the subtree draws, including text, images and other extensions, without changing that content's code. Group opacity fades a subtree as one image, so overlapping children don't show through each other.
  • Limits: each effect captures its region, so use them for regions, not for every element.

Native and wgpu producers

Backend custom-draw contexts: WgpuCustomContext, Dx11CustomContext and MetalCustomContext. Implement a producer and record your own GPU commands on the window's device into an output texture that GPUI composes in order.

  • Use for: anything the WGSL subsets can't express: compute passes, your own textures and pipelines, existing Metal, HLSL or wgpu rendering code.
  • Why it's special: full access to the GPU API on the host device, with GPUI still handling placement, clipping, opacity, caching and retirement. The wgpu context is portable across Vulkan, Metal, DX12 and the browser; the native contexts give you Metal and D3D11 directly.
  • Limits: you own correctness on each backend you target, and the work runs on the window's device and frame. For a pipeline that runs on its own, see GPU interop.

Your own pipeline: GPU interop

xgpui-gpu-interop. Every option above runs inside GPUI's renderer: on the window's GPU device, as part of its frame. GPU interop is the exception. Your engine is a completely separate pipeline with its own device, queue, thread and frame loop, presenting finished frames into an EngineSurface the way it would present to a swapchain.

  • Use for: game engines, 3D viewports, simulations, image pipelines, long compute passes, and anything with its own render loop or frames too heavy for GPUI's frame budget.
  • Why it's special: there are no restrictions on what the engine does: any shaders, render passes, compute, resources and frame rate, in wgpu (macOS, Linux, Windows) or raw Metal (macOS). Frames reach the window through a shared texture ring with zero copies and GPU-side synchronisation (IOSurface and MTLSharedEvent on macOS, Vulkan external memory and timeline semaphores on Linux, shared D3D12 textures and fences on Windows). Because the pipelines are separate, a slow or misbehaving engine can't freeze the UI: the last ready frame stays on screen. Device loss is recoverable, and heavy mode splits engine work into short submissions so the UI keeps its frame rate even when engines saturate the GPU. RGBA16F slots carry wide-gamut linear Display P3 and accept compute-shader writes directly.
  • Limits: the engine must use the same GPU as the window; there is no automatic adapter matching. Linux shows wide content as an sRGB preview for now.
