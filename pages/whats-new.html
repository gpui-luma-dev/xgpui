GPU interop — first alpha release

xgpui-gpu-interop 0.1.0 presents frames from your own GPU engine in xgpui windows without copies on macOS, Linux and Windows. The engine keeps its own device, queue and thread. Shared texture rings, GPU synchronization, wide-gamut RGBA16F output, device recovery and heavy-engine pacing support independent render and compute workloads.

Seven additive backend hooks require xgpui-apple 4.1.0, xgpui-wgpu 2.3.0 and xgpui-windows 2.2.0; existing applications need no source migration. The engine must use the compositor’s GPU. AMD and NVIDIA are untested; Linux wide content uses an sRGB preview. Read the GPU interop guide and crate keywords and contact information.

GPU device-loss reporting

When GPU recovery gives up, windows stop drawing and App::on_gpu_device_lost tells the application once, while input and timers continue. Core 3.2.0 adds the scoped notification; Linux and Windows implement bounded recovery. See the individual API and compatibility notes.

Color accuracy, examples and documentation

xgpui-color 0.3.2 derives exact OkLab inverse matrices, reducing round-trip drift from about 1e-7 to about 1e-15 without changing signatures or serialized formats. Try the GPU Canvas Workbench, GPU interop lab and threaded boids example. Static website migration updates the packaged README links; the documentation-only patch bumps below ship those changes.

November 5, 2026 — variable fonts

Variable fonts now work through the full text pipeline on macOS and Windows. xgpui 3.0.0 adds precise axis settings and OpenType inspection; xgpui-parley 0.4.0 adds matching shaping support and a quantized preview utility. The native and Parley text-lab panels expose live weight, width, slant and optical size controls. The labs and tests were confirmed working on both platforms.

Live variable-font controls and inspection

Set Font::variations or use .font_variations(...) on styled elements. FontTag::WEIGHT, WIDTH, SLANT, OPTICAL_SIZE, and ITALIC provide typed constants for the standard axes, so ordinary code needs no string parsing. Custom tags still support validated parsing, and serialized tags stay unchanged.

Signed, finite coordinates preserve negative slant and fractional author values. Each resolved face clamps supported axes to its own range; fallback runs retain the request and resolve their own coordinates. Explicit settings take precedence over corresponding implicit weight/style axes. Metrics, wrapping, caret/selection geometry and rasterization use the same resolved instance. Explicit optical size stays fixed when text size changes; automatic optical sizing remains separate.

TextSystem::font_axes, opentype_features, and font_capabilities support font inspectors without hard-coded tag lists. Results distinguish unsupported queries, successful empty lists and errors. Existing FontFeatures continues to accept numeric feature parameters. Core privately parses the metadata; the additive PlatformTextSystem::font_table hook obtains bytes from CoreText, DirectWrite, native Cosmic or Parley's actual resolved face. No helper crate or public parser API is added.

Try the native/Parley comparison and run its tests from the repository root:

just text --backend both
just lab-test

Both panels have independent sliders, keyboard/accessibility controls, presets, two specimen sizes and a live advance measurement. Arrow keys adjust settings, Shift makes larger steps, and Home/End reach the limits. Tests use backtraces by default. A Windows interaction-test setup fix now uses real DirectWrite instead of the headless platform's no-op text system.

VariationPreview quantizes before font resolution so shaping and painting agree. The lab limits each window to 512 admitted combinations and holds its last preview when full. This does not promise globally bounded memory or atlas reclamation. Frame-safe eviction, automatic optical sizing and Cosmic/browser axis parity remain separate work. Native/Parley raster differences are expected; a subtle cross-platform slant appearance difference was observed in both panels, with matching endpoints and no functional failure.

The Wasm font inspector brings these same GPUI sliders and metadata queries to the browser using Parley in Wasm. Choose WebGPU or WebGL2 for rendering; shaping and rasterization stay in Rust. Native CoreText/DirectWrite comparison remains in the desktop lab.

Read the font-controls guide for API examples, backend capabilities, preview policy and migration details.

Cosmic font inspection

Linux's default Cosmic backend now reads OpenType features and variable-axis ranges from its resolved font files, including the correct face in collections. Core performs the private metadata parsing. Missing tables, failed reads and invalid IDs retain distinct results. The native text-lab panel shows this metadata independently of whether axis editing is available.

This is inspection support: arbitrary axis application still requires additional Cosmic shaping/metrics/raster work. Parley remains the axis-capable Linux option. Linux validation includes the Cosmic and Parley suites, a headless native-host construction/axis smoke test, and shared slider interaction tests. Physical Wayland/X11 output and Linux IME/accessibility remain separate acceptance checks. The Linux DMA-BUF import path also uses the current completion guard to retain imported textures until preparation commands finish.

Core 3.0 migration

Exhaustive struct literals need three new fields: Font::variations, TextStyle::font_variations, and TextStyleRefinement::font_variations. Use Default::default() for the first two and None for refinements; exhaustive patterns can use ... Calls using constructors/defaults generally need only a recompile. Empty settings retain existing axis behavior. Upgrade matching backend and extension pins together; the remaining inspection APIs are additive, and custom backends inherit unsupported defaults. See the API migration guide.

Metal rendering and photo viewports

Dense custom-rendered scenes no longer need a separate pending command buffer for every producer. Producers encode through MetalCustomContext::record into one shared preparation batch, and the host validates and submits the work. This fixes command-buffer exhaustion during dense preparation. A supervised 512-producer regression covers replay, scene replacement and pixel correctness. The objc2 resource ownership model is retained. (Rendering update #121)

Large photos refine while keeping an overview visible. The media extension’s RasterSource builds requested mip pages from bounded decoded pixels and RGB metadata, using linear-light, alpha-aware filtering. A source replacement keeps the previous overview visible as new pages become ready. CanvasPaint selects wide SDR or an sRGB preview and applies existing GPU image adjustments without rebuilding source pages or uploading them again. Admission retry also handles workers that are still retiring. Applications retain control of decoding and source limits; page allowances do not represent total GPU memory.

Smoother Mandelbrot navigation

The native canvas lab now keeps a complete frame on screen and reprojects it while a replacement prepares offscreen. Shallow views use cached Metal compute into linear-P3 float textures on supported macOS wide-SDR hosts. Deeper views use background CPU calculation with preview and detail refinement. Frames replace each other as complete images, avoiding partial tile boundaries during navigation. (Canvas update #108)

October 31, 2026

Color and wide gamut, from source pixels to the display

XGPUI’s expanded color pipeline connects sRGB, Display P3, Adobe RGB (1998) and Rec.2020 through explicit conversion, image storage and native wide-gamut rendering. It covers everyday UI colors, wide-gamut photographs, perceptual color editing and custom RGB profiles. Applications choose their own image decoder and supply pixels plus color metadata to the library.

  • Choose the space for the task. sRGB remains the basis for ordinary UI and portable previews. Display P3 supports wide-gamut content and P3 image storage. Adobe RGB (1998) adds a photographic source space, while Rec.2020 provides wider SDR image storage that can retain Adobe RGB colors outside P3. Each source keeps its declared primaries and transfer function during conversion.
  • Convert, inspect and interpolate. Move between the four named RGB spaces, inspect XYZ and chromaticity coordinates, and use OkLab/OkLCh for perceptual color operations and gradients. Explicit gamut mapping controls how colors fit the destination; D50/D65 white-point adaptation supports custom definitions and profile interpretation. See the color math guide.
  • Preserve wider colors. Use Display P3 or Rec.2020 image storage deliberately, then retain extended color values through native composition, normal blending, blur and linear color filters until output mapping. Ordinary UI colors remain sRGB; choosing Rec.2020 storage does not enable HDR.
  • Interpret the source correctly. Named color spaces, custom RGB definitions and extended linear pixels share the supplied-pixel pipeline, with explicit transfer curves, alpha handling and gamut mapping.
  • Use embedded RGB profiles. The optional ICC adapter resolves a bounded matrix/TRC subset, including sampled and parametric curves and white-point adaptation. It preserves the profile’s actual values and reports unsupported profiles explicitly. See supported ICC profiles.
  • Check the numbers and the rendering. Independent high-precision references cover RGB conversion, white-point adaptation, profile curves, near-black values and alpha. Metal FP16 readback checks native composition before display color management, including colors that an ordinary sRGB screenshot cannot retain.

Wide gamut is a capability; Display P3 is a particular color space. Source interpretation, image storage, window presentation and the physical display are separate choices. The new practical color guides, pixels and metadata guide and lab walkthroughs explain common tasks without requiring a color science background. The color overview includes small examples for everyday conversions, mapping and image input.

Try the new browser examples:

  • Chromaticity and gamut: explore gamut boundaries, luminance and mapping with an sRGB chart preview.
  • Pixels + metadata: keep the samples fixed while changing their interpretation; guided lessons show when to inspect XYZ values and packed FP16 bytes rather than expect a large visual change.
  • Italy photo comparison: compare WebKit’s sRGB, Display P3 and highlighted photographs, or switch the selected photo between its browser-managed original and a Rust/Wasm sRGB preview.

The gallery now contains 24 examples. The Italy example uses browser image color management; the GPUI web canvas demos remain sRGB previews. Apple bindings: why, what and impact

Why. The legacy Cocoa/metal-rs dependency paths brought in block 0.1.6, which triggers a Rust future-incompatibility warning. Moving to the maintained objc2 framework bindings removes those paths from normal macOS rendering and windowing, and makes Objective-C object ownership explicit in Rust types.

What changed. Metal rendering, atlas textures, custom producers and shader caches now use objc2 Metal handles. The macOS window, event, display, clipboard and display-link code uses objc2 AppKit/Foundation bindings. CoreVideo sampling also retains its texture views and cache until GPU work finishes, releasing views before the cache so queued frames can survive renderer teardown.

Impact on applications. Ordinary GPUI views largely keep the same APIs. Custom Metal integrations need source changes: public device/queue fields and texture/command handles now use objc2 types instead of metal-rs types. This is why xgpui-apple and xgpui-macos moved to 2.0.0, and media's exposed Apple types moved with xgpui-media 0.3.0. Update related crate pins together and review conversions at your native producer boundary.

Watch for:

  • Resource lifetime: closing windows or destroying renderers with queued GPU work; rapid video/frame replacement; stale cached textures. Keep ownership explicit, and record producer work on the host's device and queue.
  • Native behavior: keyboard shortcuts and IME, clipboard operations, focus, resizing, display changes and wide-gamut output. Exercise these in your app; successful compilation does not establish runtime correctness.
  • Optional legacy dependencies: screen capture can still bring older bindings through zed-scap. Check enabled-feature dependency trees before assuming every optional path is free of block 0.1.6.

The release passed package verification and a registry-only macOS consumer check. Native Windows/Linux runtime coverage and app-specific lifecycle testing remain separate checks. See GPUI API changes for integration contracts.
