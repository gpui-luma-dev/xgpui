XGPUI 5.0.0 — GPUI 1.29.3 and Canvas spatial editing

The GPUI sources follow gpui-unofficial 1.29.3 (Zed v1.29.3); 1.29.1 and 1.29.2 changed no GPUI sources. Where an upstream change conflicted with XGPUI behavior, XGPUI’s behavior was kept (#406). Canvas gains spatial editing APIs. xgpui 5.0.0 has compile-breaking changes, so every crate that exposes its types takes a breaking version; 18 crates are published, and xgpui-color and xgpui-macros are unchanged.

Highlights

  • Elements: every Element is an IntoElement through a blanket impl, and Div keeps its interactivity out of line, so builder chains copy far less.
  • Text: shaped lines share their text with the layout cache, line backgrounds are skipped when there are none, and on the wgpu text path combining marks sit over their base letter.
  • Windows: color (COLR) glyph layers are composited on the CPU, so the text system no longer holds DirectX resources.
  • macOS: menu shortcuts bound to backspace and delete fire.
  • Wayland: frame callbacks are timed from receipt, since the protocol leaves the compositor clock unspecified.
  • Core: list() respects horizontal padding and borders, a drag’s cursor applies immediately, animated WebP images decode every frame, and GraphicalEnvironment::desktop_environment() reports the Linux desktop.
  • Canvas spatial editing (#384): camera centering and padded fitting, indexed queries and front-to-back picking candidates, separate geometry and content invalidation, mutable item data, atomic batch bounds updates and explicit index rebuild, with a mixed-shape editor demo (just canvas editor).

Bug fixes

  • Canvas: pan and zoom update atomically, invalid viewport, scene-bounds, snapping and grid inputs are rejected, and extreme finite coordinates no longer overflow (#383).
  • Gestures: pinch gestures reach their listeners while keyboard focus suppresses hover styling (#404).

Migration

Some changes stop existing code from compiling; each is listed with its fix on the GPUI 1.29.3 migration page. The most common: delete any impl IntoElement next to an impl Element. Update the GPUI family together. The full record is in the API ledger and the upstream change accounting.

Validation

CI passed on the merge into main, including real-window Linux (Wayland and X11), Windows and macOS jobs. Windows and Linux were checked by hand, Windows at several zoom levels. xgpui-luma built and passed all its tests against the release candidate after removing five IntoElement impls.

xgpui-curve 0.1.0 — curves for editors, charts and gradients

A new extension crate, xgpui-curve, gives xgpui one place for curve math: the geometry, splines, editing models and shader helpers that apps used to write themselves. Three crates are published: xgpui-curve 0.1.0 (new), xgpui-svg 0.4.2 and xgpui-macos 5.0.2. No GPUI changes are needed, no migration is required, and the other 17 crates are unchanged. Release issue #390; release notes on GitHub releases.

Highlights

  • Curves you can touch. Nearest point with signed distance, curve–curve intersection, hit testing on fills and strokes, and exact bounds, so you can click, hover and snap to curves, not just draw them.
  • Plot lines and easing. Twelve d3-style series curves, including monotone lines that never overshoot your data, area fills, viewport clipping, PCHIP tone curves with LUT baking, and CSS cubic-bezier(), steps() and linear().
  • Mesh-gradient wireframes that match the render. MeshLattice gives the exact cubic edges of a Hermite mesh, explicit or automatic tangents, and a wire drag that keeps the grabbed point under the cursor.
  • Fields that bend. CurveSpine projects any pixel onto a curve, with the same math in Rust, WGSL and Metal, and a seam rule that keeps the projection continuous.
  • A node editor model. Corner, Smooth, Symmetric, Catmull-Rom, natural and Hobby nodes with edits that keep each constraint, and shape-preserving insertion.
  • Shapes and ink. Squircles with continuous-curvature corners, padded arc sectors, variable-width tapered strokes, freehand fitting, trim and dash, and SVG path data.

Try it

The curve lab has six panels, with wheel or pinch zoom and pan: just curve on the desktop, or the browser demo. Read the curves guide for examples.

Bug fixes

  • macOS: closing a window no longer logs handling active status change … window not found (#371).

Deprecated

xgpui_svg::path_effects (Contour, Segment, MeasuredPath, PathEffect) now delegates to xgpui-curve, behaves as before, and is deprecated; it will be removed in a later release. Use xgpui_curve::measure::{MeasuredPath, PathEffect} on a kurbo::BezPath, and stroke the result with xgpui_curve::gpui_paint::append into a PathBuilder::stroke. See measure and SVG.

Validation

CI passed on the merge into main. Windows and Linux were checked by hand on main.

XGPUI 4.2.0 — plain GPUI text on Parley paragraphs

Standard GPUI text handles wrapped right-to-left and mixed text on Parley. Two crates are published: xgpui 4.2.0 and xgpui-parley 0.8.0. Both are additive: no migration is needed, and the other 17 crates are unchanged. Release issue #359; release notes on GitHub releases.

Highlights

  • Right-to-left in plain GPUI text (#332): call xgpui_parley::install_text_layout(parley, cx) once, and every plain text element (div().child("…"), StyledText, InteractiveText, tooltips, list rows, third-party widgets) is laid out by the engine behind typeset(). Wrapped Hebrew, Arabic and mixed text wraps in logical order; truncation, line clamps and start/end alignment work; hit testing matches what's painted. Each paragraph's direction comes from its first strong character, so typeset() is only needed for an explicit direction or language. See Right-to-left text.
  • Text layout provider in GPUI core (#350): TextLayoutProvider, ProvidedTextLayout and App::set_text_layout_provider let a text engine lay out GPUI's plain text elements. Without a provider, GPUI's flat lines run unchanged. See GPUI public API changes.
  • Faster paragraph paint (#351): paint_paragraph uses one paint layer per paragraph and skips glyphs outside the content mask. Plain text on Parley costs about 1.12× GPUI's lines on a warm frame and 0.95× on reflow.
  • Docs and labs: a right-to-left how-to with a runnable example (just rtl-example), a right-to-left paragraph demo in the Wasm gallery (#341), and a localization QA lab in xgpui-ext-lab (#355).

Bug fixes

  • Text: TextLayout::wrapped_text() no longer panics on wrapped right-to-left text, on any backend (#352).

Opting in changes layout

Only for apps that call install_text_layout. Native backends, and apps that don't call it, get no layout change.

  • text_align Left/Right act as start/end, so they mirror for right-to-left text.
  • Min-content is the longest word instead of the full line, which can change flex shrink results.
  • Wrap points follow Parley. Truncation keeps the logical start.
  • TextLayout::line_layouts() is empty and line_layout_for_index() returns None; use index_for_position and position_for_index.

Validation

CI passed on the merges into main. Windows and Linux were checked by hand on main. The text-lab checks cover logical wrap order and the right-to-left page on Parley, with native output unchanged. xgpui-luma builds against the release candidate and its tests pass.

XGPUI 4.1.0 — paragraph text, ProPhoto RGB and GPU interop pacing

Paragraph text through GPUI on every backend, right-to-left text in plain GPUI labels, ProPhoto RGB, and frame pacing for GPU interop engines. 19 crates are published: xgpui 4.1.0, breaking minor versions of five extensions, and patch versions of the rest. Release issue #338; release notes on GitHub releases.

Highlights

  • Paragraph text through GPUI (#325): text controls get one paragraph engine through window.text_system(). paragraph_support() reports Unsupported, LeftToRight or Full; layout_paragraph_with_options takes a base direction (TextDirection) and a language; paragraph_content_widths gives min-content and max-content widths; layouts provide hit testing, carets, visual movement and selection. Parley gives full bidirectional layout. Native backends get a built-in fallback: lines wrap in order and align to the base direction's start edge, so Hebrew sits on the right, and glyph order within a line comes from the platform shaper. See Paragraphs and input.
  • Right-to-left in plain GPUI text: on Parley, single-line Hebrew, Arabic and mixed labels render (#330). On every backend, per-run colors, backgrounds and underlines paint correctly for right-to-left text (#333). Wrapping and carets in plain text stay left-to-right (#332); use typeset() for those.
  • ProPhoto RGB (ROMM RGB, D50) in xgpui-color (CPU and WGSL) and as a source interpretation in xgpui-media (#107). See color math.
  • GPU interop pacing (#262): wait_composited, on_composited, refresh_interval, and Presentation::{GpuWait, ObserveOnly, Auto}. The API review (#261) adds request_device on every platform and a typed Unsupported. See GPU interop.
  • Labs: just text bidi shows GPUI paragraphs and right-to-left labels side by side on native and Parley.

Bug fixes

  • Windows: closing a window no longer logs "Invalid window handle" errors (#277).
  • Native paragraphs: right-to-left text from CoreText wraps inside its box instead of running off the left edge (#336).
  • Builds: warning-free builds, macro tests and a Clippy policy (#280).

Migration

  • xgpui 4.1: build a ParagraphRequest with ParagraphRequest::new, not a struct literal; only text backends that construct requests are affected. layout_paragraph now succeeds on native backends and the test platform; check paragraph_support() instead of the error. See GPUI public API changes.
  • xgpui-color 0.4: add a wildcard arm to matches on RgbSpace and GamutMapping.
  • xgpui-media 0.7: add a wildcard arm to matches on ImagePrimaries and TransferFunction.
  • xgpui-gamut 0.5: follows xgpui-color 0.4 through its color re-export.
  • xgpui-gpu-interop 0.3: add a wildcard arm to matches on Transport, AcquireError, SurfaceFormat, SurfaceStats and HeavyStatus; EngineSurface::unsupported() returns Option<Unsupported> (use .reason()); EngineSurface::paint takes cx; SurfaceFormat::color_mode is no longer public.
  • xgpui-parley 0.7: TextDirection is gpui::TextDirection, re-exported with the same variants; the From conversion to Parley's BaseDirection is gone.

Validation

Every change passed PR CI. macOS runners were unavailable for the final merge, so the macOS warnings job ran locally on the same commit, with no warnings. Windows and Linux were checked by hand on main. The paragraph work is covered by core tests, CoreText tests with a Hebrew font, Parley tests, and xgpui-luma's lab tests on Parley and on the native text system.

November 15, 2026 — GPUI 1.28.1 upstream sync

The GPUI sources now follow gpui-unofficial 1.28.1 (Zed v1.28.1). Where an upstream change conflicted with XGPUI behavior, XGPUI’s behavior was kept. The release is available on crates.io: 17 new crate versions, from tag release-2026-11-15-04ba149f08ca; xgpui-color and xgpui-macros are unchanged. Tracking issue #284. Every change, migration step and version reason: GPUI 1.28.1 sync: changes and migration. Full release notes on GitHub.

Highlights

  • macOS frame pacing: on macOS 14 and later, windows draw from CAMetalDisplayLink. Animation runs at the display rate instead of stalling at about 30 fps, and idle windows stop drawing. Earlier systems keep CVDisplayLink.
  • Text: ICU grapheme-aware wrapping, right-to-left and shaped-cluster breaks, a CoreText point-size fix, and invisible tab glyphs on DirectWrite.
  • Wayland: activation requests no longer overwrite each other (no stuck GNOME launch indicator), blur through ext-background-effect-v1 with a KDE fallback, and blur and input regions that follow client corner radii.
  • Windows: repeated synthetic mouse moves are dropped, and real moves, drags and arrivals are still delivered.
  • wgpu: the window surface is configured once at creation, removing 200–500 ms before the first frame on slow drivers. Bounded device-loss recovery is unchanged.
  • Core: configurable low-power and thermal frame intervals with the same defaults as before; cx.notify() redraws stay unthrottled. Send-capable foreground executors, Window::set_client_corner_radii, and cached-view opacity fixes.
  • Desktop shell: xgpui-shell 0.3.0 adds a window-control presenter hook and native caption clicks on Windows (#194), and keeps the app-controlled title-bar colors from 0.2.0 (#192).

Bug fixes

  • Windows pointer: leaving the window now sends MouseExited, so hover states and popovers clear; moving between the client area and the title bar doesn't count. The cursor set in WM_SETCURSOR is no longer overridden (#267, #70).
  • Windows maximize: Window::zoom_window restores a maximized window, matching its documented toggle on macOS and Linux (#278).
  • Windows drawing: color-mode changes requested during a draw no longer fail (#302), and a shader DirectX cannot compile no longer stops the window drawing (#303).
  • Wayland diagnostics: frame-loop trace logging under xgpui::wayland::frame and a one-time warning when a frame callback is outstanding for over 500 ms, added while investigating the GNOME stall, which no longer reproduces (#276, #271).

The typography lab can also validate wide-gamut SDR presentation of glow and shadow effects (#282).

Migration

  • WindowOptions has two new fields, low_power_frame_interval and thermal_frame_interval. Struct literals that list every field need them or ..Default::default().
  • gpui::http_client no longer re-exports the GitHub download helpers or anyhow. Depend on anyhow directly.
  • AppCell::try_borrow_mut returns anyhow::Result. Only code that names BorrowMutError needs changes.
  • WgpuContext::new and new_rejecting_software take the &WgpuSurfaceConfig the renderer will use. Code that creates renderers through WgpuRenderer is unaffected.
  • ShellControl is non-exhaustive; add a wildcard arm to matches.

Update the GPUI family together: xgpui 4 types are distinct from 3.x types. Every change is listed with its compatibility notes in the API ledger and the upstream change accounting.

Validation

Each backend’s test suite runs in CI, along with real-window checks. On macOS, display-rate animation (about 60 fps), no frames while idle, and a live screenshot. On Windows, synthetic mouse-move filtering. On Wayland, protocol checks under Weston and headless Mutter (activation tokens requested, returned and used in pairs) and an X11 run under Xvfb. All 19 crate archives pass offline inspection and the publication-order check; the iOS backend compiles for the simulator. All 17 uploads were verified against crates.io, and a fresh project using only crates.io built and ran on macOS. Interactive iOS validation and physical-display gamut checks are not covered.

November 12, 2026 — GPU interop and device-loss recovery

The November 12 release is available on crates.io: 18 new crate versions, including the first xgpui-gpu-interop 0.1.0 release. Source tag: release-2026-11-12-da99e6bb8e6d. The iOS crate remains at 1.26.5.

GPU interop — first alpha release

xgpui-gpu-interop 0.1.0 presents frames from your own GPU engine in xgpui windows without copies on macOS, Linux and Windows. The engine keeps its own device, queue and thread. Shared texture rings, GPU synchronization, wide-gamut RGBA16F output, device recovery and heavy-engine pacing support independent render and compute workloads.

Seven additive backend hooks require xgpui-apple 4.1.0, xgpui-wgpu 2.3.0 and xgpui-windows 2.2.0; existing applications need no source migration. The engine must use the compositor’s GPU. AMD and NVIDIA are untested; Linux wide content uses an sRGB preview. Read the GPU interop guide and crate keywords and contact information.

GPU device-loss reporting

When GPU recovery gives up, windows stop drawing and App::on_gpu_device_lost tells the application once, while input and timers continue. Core 3.2.0 adds the scoped notification; Linux and Windows implement bounded recovery. See the individual API and compatibility notes.

Color accuracy, examples and documentation

xgpui-color 0.3.2 derives exact OkLab inverse matrices, reducing round-trip drift from about 1e-7 to about 1e-15 without changing signatures or serialized formats. Try the GPU Canvas Workbench, GPU interop lab and threaded boids example. Static website migration updates the packaged README links; the documentation-only patch bumps below ship those changes.

November 5, 2026 — variable fonts

Variable fonts now work through the full text pipeline on macOS and Windows. xgpui 3.0.0 adds precise axis settings and OpenType inspection; xgpui-parley 0.4.0 adds matching shaping support and a quantized preview utility. The native and Parley text-lab panels expose live weight, width, slant and optical size controls. The labs and tests were confirmed working on both platforms.

Live variable-font controls and inspection

Set Font::variations or use .font_variations(...) on styled elements. FontTag::WEIGHT, WIDTH, SLANT, OPTICAL_SIZE, and ITALIC provide typed constants for the standard axes, so ordinary code needs no string parsing. Custom tags still support validated parsing, and serialized tags stay unchanged.

Signed, finite coordinates preserve negative slant and fractional author values. Each resolved face clamps supported axes to its own range; fallback runs retain the request and resolve their own coordinates. Explicit settings take precedence over corresponding implicit weight/style axes. Metrics, wrapping, caret/selection geometry and rasterization use the same resolved instance. Explicit optical size stays fixed when text size changes; automatic optical sizing remains separate.

TextSystem::font_axes, opentype_features, and font_capabilities support font inspectors without hard-coded tag lists. Results distinguish unsupported queries, successful empty lists and errors. Existing FontFeatures continues to accept numeric feature parameters. Core privately parses the metadata; the additive PlatformTextSystem::font_table hook obtains bytes from CoreText, DirectWrite, native Cosmic or Parley's actual resolved face. No helper crate or public parser API is added.

Try the native/Parley comparison and run its tests from the repository root:

just text --backend both
just lab-test

Both panels have independent sliders, keyboard/accessibility controls, presets, two specimen sizes and a live advance measurement. Arrow keys adjust settings, Shift makes larger steps, and Home/End reach the limits. Tests use backtraces by default. A Windows interaction-test setup fix now uses real DirectWrite instead of the headless platform's no-op text system.

VariationPreview quantizes before font resolution so shaping and painting agree. The lab limits each window to 512 admitted combinations and holds its last preview when full. This does not promise globally bounded memory or atlas reclamation. Frame-safe eviction, automatic optical sizing and Cosmic/browser axis parity remain separate work. Native/Parley raster differences are expected; a subtle cross-platform slant appearance difference was observed in both panels, with matching endpoints and no functional failure.

The Wasm font inspector brings these same GPUI sliders and metadata queries to the browser using Parley in Wasm. Choose WebGPU or WebGL2 for rendering; shaping and rasterization stay in Rust. Native CoreText/DirectWrite comparison remains in the desktop lab.

Read the font-controls guide for API examples, backend capabilities, preview policy and migration details.

Cosmic font inspection

Linux's default Cosmic backend now reads OpenType features and variable-axis ranges from its resolved font files, including the correct face in collections. Core performs the private metadata parsing. Missing tables, failed reads and invalid IDs retain distinct results. The native text-lab panel shows this metadata independently of whether axis editing is available.

This is inspection support: arbitrary axis application still requires additional Cosmic shaping/metrics/raster work. Parley remains the axis-capable Linux option. Linux validation includes the Cosmic and Parley suites, a headless native-host construction/axis smoke test, and shared slider interaction tests. Physical Wayland/X11 output and Linux IME/accessibility remain separate acceptance checks. The Linux DMA-BUF import path also uses the current completion guard to retain imported textures until preparation commands finish.

Core 3.0 migration

Exhaustive struct literals need three new fields: Font::variations, TextStyle::font_variations, and TextStyleRefinement::font_variations. Use Default::default() for the first two and None for refinements; exhaustive patterns can use ... Calls using constructors/defaults generally need only a recompile. Empty settings retain existing axis behavior. Upgrade matching backend and extension pins together; the remaining inspection APIs are additive, and custom backends inherit unsupported defaults. See the API migration guide.

Color and wide gamut, from source pixels to the display

XGPUI’s expanded color pipeline connects sRGB, Display P3, Adobe RGB (1998) and Rec.2020 through explicit conversion, image storage and native wide-gamut rendering. It covers everyday UI colors, wide-gamut photographs, perceptual color editing and custom RGB profiles. Applications choose their own image decoder and supply pixels plus color metadata to the library.

  • Choose the space for the task. sRGB remains the basis for ordinary UI and portable previews. Display P3 supports wide-gamut content and P3 image storage. Adobe RGB (1998) adds a photographic source space, while Rec.2020 provides wider SDR image storage that can retain Adobe RGB colors outside P3. Each source keeps its declared primaries and transfer function during conversion.
  • Convert, inspect and interpolate. Move between the four named RGB spaces, inspect XYZ and chromaticity coordinates, and use OkLab/OkLCh for perceptual color operations and gradients. Explicit gamut mapping controls how colors fit the destination; D50/D65 white-point adaptation supports custom definitions and profile interpretation. See the color math guide.
  • Preserve wider colors. Use Display P3 or Rec.2020 image storage deliberately, then retain extended color values through native composition, normal blending, blur and linear color filters until output mapping. Ordinary UI colors remain sRGB; choosing Rec.2020 storage does not enable HDR.
  • Interpret the source correctly. Named color spaces, custom RGB definitions and extended linear pixels share the supplied-pixel pipeline, with explicit transfer curves, alpha handling and gamut mapping.
  • Use embedded RGB profiles. The optional ICC adapter resolves a bounded matrix/TRC subset, including sampled and parametric curves and white-point adaptation. It preserves the profile’s actual values and reports unsupported profiles explicitly. See supported ICC profiles.
  • Check the numbers and the rendering. Independent high-precision references cover RGB conversion, white-point adaptation, profile curves, near-black values and alpha. Metal FP16 readback checks native composition before display color management, including colors that an ordinary sRGB screenshot cannot retain.

Wide gamut is a capability; Display P3 is a particular color space. Source interpretation, image storage, window presentation and the physical display are separate choices. The new practical color guides, pixels and metadata guide and lab walkthroughs explain common tasks without requiring a color science background. The color overview includes small examples for everyday conversions, mapping and image input.

Apple bindings: why, what and impact

Why. The legacy Cocoa/metal-rs dependency paths brought in block 0.1.6, which triggers a Rust future-incompatibility warning. Moving to the maintained objc2 framework bindings removes those paths from normal macOS rendering and windowing, and makes Objective-C object ownership explicit in Rust types.

What changed. Metal rendering, atlas textures, custom producers and shader caches now use objc2 Metal handles. The macOS window, event, display, clipboard and display-link code uses objc2 AppKit/Foundation bindings. CoreVideo sampling also retains its texture views and cache until GPU work finishes, releasing views before the cache so queued frames can survive renderer teardown.

Impact on applications. Ordinary GPUI views largely keep the same APIs. Custom Metal integrations need source changes: public device/queue fields and texture/command handles now use objc2 types instead of metal-rs types. This is why xgpui-apple and xgpui-macos moved to 2.0.0, and media's exposed Apple types moved with xgpui-media 0.3.0. Update related crate pins together and review conversions at your native producer boundary.

Watch for:

  • Resource lifetime: closing windows or destroying renderers with queued GPU work; rapid video/frame replacement; stale cached textures. Keep ownership explicit, and record producer work on the host's device and queue.
  • Native behavior: keyboard shortcuts and IME, clipboard operations, focus, resizing, display changes and wide-gamut output. Exercise these in your app; successful compilation does not establish runtime correctness.
  • Optional legacy dependencies: screen capture can still bring older bindings through zed-scap. Check enabled-feature dependency trees before assuming every optional path is free of block 0.1.6.

The release passed package verification and a registry-only macOS consumer check. Native Windows/Linux runtime coverage and app-specific lifecycle testing remain separate checks. See GPUI API changes for integration contracts.
