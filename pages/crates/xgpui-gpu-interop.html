Why GPU interop

GPUI renders everything inside its own frame, on its own GPU device. That is right for UI, but it leaves no good home for GPU work that is not UI: a simulation, an image pipeline, a long compute pass, a game or 3D view. Stock GPUI can paint images, and on macOS CoreVideo pixel buffers, but it cannot show a texture that your device rendered.

Without this crate there are two workarounds, and both hurt. Read the frame back to the CPU and upload it again as an image every frame, which costs copies, bandwidth and latency. Or move the work into GPUI's paints, where a slow pass stalls the whole UI. xgpui-gpu-interop instead shares a small ring of textures between your engine's device and xgpui's compositor, with native GPU signals on macOS, Linux and Windows, so the engine presents frames like it would to a swapchain and nothing is copied.

Example: an engine on its own thread

The engine keeps its device, queue and thread; the window just paints the surface. Device creation and the render code are omitted:

// Engine thread: your own wgpu device, queue and pipelines.
let target = WgpuSurfaceTarget::new(SurfaceDesc {
    width: 640,
    height: 400,
    format: SurfaceFormat::Rgba16FloatLinearP3, // or Bgra8Srgb
    slots: 3,
}, &device, &queue)?;
let surface = target.surface().clone(); // hand this to the view

loop {
    let slot = target.surface().acquire()?;      // a free texture in the shared ring
    render_into(target.texture(&slot)?)?;        // render or run compute into it
    target.present(slot, [encoder.finish()])?;   // submit, then publish the frame
    target.surface().wait_composited(Duration::from_millis(100)); // pace to the display
}

// UI: in an element's paint phase, show the newest frame. No copies.
surface.paint(window, cx, bounds, corner_radii);

A slow engine never blocks the UI: turn on Presentation::Auto or heavy-engine mode and the window keeps showing the last finished frame. See the pacing guide.

Public surface at a glance

EngineSurface, SurfaceSlot, SurfaceDesc, SurfaceFormat, SurfaceStats, SyncPoint, HeavyEngine and the wgpu-feature WgpuSurfaceTarget adapter; IOSurface/MTLSharedEvent on macOS, opaque-fd memory and timeline semaphores on Linux, shared D3D12 textures and fences on Windows.

Dependencies

Dependencies, optional features and target conditions are declared in Cargo.toml ↗.

It uses additive backend hooks in xgpui-apple, xgpui-wgpu and xgpui-windows; Cargo selects the matching versions. The optional wgpu feature enables the engine adapter; Linux and Windows require it for the transport.
