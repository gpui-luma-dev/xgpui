GPUI public API changes: additions and compatibility

This crate requires per-window color request/status APIs and typed wide-SDR backend outputs. PlatformWindow supplies default request/report methods, so existing platform implementations need no required overrides. Default windows and legacy sRGB paints retain their behavior; additive method names can still collide with downstream extension methods.

It reuses the custom-content recording changes: complete Scene literals must include custom_draws, and exhaustive Primitive / PrimitiveBatch matches must handle Custom. Window-option structs and existing ordinary output types retain their contracts. New color configuration/fallback enums are non-exhaustive.

Metal compositing contract

scene: UI background → wide A → controls → wide B → tooltip

1. legacy renderer → transparent sRGB scratch → convert/composite
2. wide A         → linear P3 composition target
3. legacy renderer → cleared scratch         → convert/composite
4. wide B         → linear P3 composition target
5. legacy renderer → cleared scratch         → convert/composite
6. tagged window presentation

A UI run is a maximal consecutive sequence of legacy draws between wide draws. Scratch is consumed before clearing/reusing it, in GPU command order. Do not flatten all UI into a top overlay. Native overlays, surface children, paths, masking and replay retain scene order.

// UI scratch: associated encoded sRGB, aligned texel reads.
A       = sampled alpha
C       = A > 0 ? sampled RGB / A : 0
L       = srgb_decode_piecewise(C)
P       = linear_srgb_to_linear_p3(L)
source  = (A * P, A)

// Wide output is already associated linear P3; filter in that representation.
k       = host coverage * inherited opacity
src     = (k * source.rgb, k * source.a)
out.rgb = src.rgb + dst.rgb * (1 - src.a)
out.a   = src.a   + dst.a   * (1 - src.a)

Opaque panels retain legacy blending within each run. Translucent controls over wide content use linear composition; exact legacy blending across that boundary is not promised. Flattening a transparent run loses individual backdrop interactions. On macOS Metal, explicit backdrop and layer boundaries flush the preceding UI run into the linear P3 target before capturing. Captures and blur scratch use premultiplied extended linear P3 RGBA16F; filtered layers restore their saved destination before applying group opacity and blending. Saturation uses P3 luminance coefficients; linear tone operations preserve extended channels. Normal blending preserves extended channels; artistic modes retain bounded operand definitions. Rec.2020 image/instanced shader sources convert to extended P3 on Metal or scRGB on Windows. P3 sources keep P3 storage, since bounded Rec.2020 maps a small P3 boundary region. Windows capture restrictions remain unchanged. Default-mode effects retain encoded-sRGB behavior, so filtered colors can differ between modes. Path-masked shader draws retain their coverage pass.

Retained capture textures are rebuilt when switching between default and wide modes. Four 1024-square layer groups remain the limit; FP16 group textures consume eight bytes per texel, with at most 128 MiB retained for groups. Backdrops retain their separate four-boundary/1024-side limits. The viewport target budget remains 256 MiB. These limits exclude driver and in-flight references.

Grayscale text coverage is supported. macOS Metal's LCD/subpixel batch remains unsupported. Low-alpha pixels are tested without an arbitrary epsilon cutoff.

Limits and acceptance

  • Full-viewport conversion per UI run and an extra Float16 presentation copy. Lab patch producers allocate on preparation; pooling/GPU timing remain future work.
  • Scratch + composition targets are capped at 256 MiB per live pair. This excludes drawable, producer, path/atlas and in-flight retention. Float16 is eight bytes/pixel.
  • Physical display/profile comparisons and device-loss stress remain outstanding. An sRGB screenshot cannot prove physical wide-gamut output.
  • Source/image profiles, RAW/video, HDR/EDR and Linux presentation remain separate milestones. Windows native execution and physical display validation remain outstanding; cross-compilation alone is not acceptance.

Typed Windows output

use anyhow::{anyhow, Result};
use gpui::{CustomContent, DevicePixels, Size};
use gpui_windows::custom_draw::Dx11CustomContext;
use std::any::Any;

#[derive(Debug)]
struct WideRed;
impl CustomContent for WideRed {
    fn prepare(&self, backend: &dyn Any, extent: Size<DevicePixels>)
        -> Result<Box<dyn Any>>
    {
        let ctx = backend.downcast_ref::<Dx11CustomContext>()
            .ok_or_else(|| anyhow!("native D3D11 required"))?;
        let output = ctx.create_wide_sdr_output(extent)?;
        ctx.record_wide_sdr(&output, |deferred, target| {
            // Associated linear P3: red at 50% alpha, not encoded sRGB.
            unsafe { deferred.ClearRenderTargetView(target, &[0.5, 0.0, 0.0, 0.5]); }
            Ok(())
        })?;
        Ok(Box::new(output)) // host alone finishes and executes the recording
    }
}

// In a producer cache, scoped by retained host context, extent and revision:
if let Some(output) = cached.as_ref().filter(|o| ctx.can_reuse_wide_sdr(o)) {
    return Ok(Box::new(output.clone()));
}
