Images and video frames. Practical examples for loading, adjusting and displaying media in GPUI.

xgpui-media

For caller-owned pixels and explicit color metadata, use pixels + metadata. The optional ICC adapter interprets supplied RGB matrix/TRC profile bytes; this does not turn the file convenience loaders below into a general color-managed decoder.

Images and GPU-backed video frames for GPUI. Use it when your app needs large photos, image adjustments, or a view of frames produced by another part of your application. The API is experimental.

Images keep a set of smaller versions called mipmaps ↗. The GPU picks a suitable level when drawing a small preview, which helps fine detail stay steady as you zoom or scroll. The native loader prepares images in the background and limits how much work can enter the renderer at once.

Linear adjustments and next pipeline contracts

Media pipeline contracts documents Phases 1–5 of issue #26: explicit linear color/alpha semantics, CPU matrix/vignette references, progressive publication states and bounded tile planning. The new ImageAdjustments placement API renders matrix/vignette effects in linear sRGB ↗ on retained RGBA8 ↗ images, without changing ImageFilter. Run just media --adjustments or use the browser Image filters demo. RGBA16F uploads, progressive/tiled rendering, bounded preview blur and native video adjustments are available; the pipeline guide describes their limits. Existing image and native surface instructions below still apply.

Beyond photos and video

Any UI that displays detailed raster content at different sizes can benefit:

  • Document previews: render a PDF page once, then reuse it in thumbnails and a larger preview.
  • Maps and diagrams: display rasterized layers or tiles while zooming; mipmaps help reduce shimmer.
  • Scientific tools: show generated heatmaps, simulation output or microscope images, with brightness and contrast controls.
  • Remote desktops and emulators: present frames produced elsewhere, keeping the latest available frame rather than accumulating stale ones.
  • Design tools: reuse cached raster previews of complex artwork while navigating a canvas.

The pixels can come from a renderer, simulation or remote source. Document rendering, map generation and remote-frame decoding still happen outside xgpui-media. For already-decoded pixels, mipmapped_rgba8 builds a mip chain; a host adapter handles the GPU upload. Native GPU frames use the video adapters described below.

For small icons and ordinary UI images, GPUI's existing img is still a useful default. You opt into xgpui-media where these features help.

Load once, display many times

Keep a MediaLoader, the pending ImageJob, and the resulting MediaImage in your view. Start a load when the user chooses an image, rather than starting it again on every render.

use xgpui_media::MediaLoader;

// Create once and retain in your view.
let loader = MediaLoader::default();
let job = loader.load("photos/cover.webp")?;
// Store job in self.pending so later renders can poll it.

Poll the job from your view or a GPUI task. Taking a completed image does not wait for decoding. These snippets assume your view has pending and photo fields:

if let Some(job) = self.pending.as_mut()
    && let Some(image) = job.try_take()
{
    self.photo = Some(image);
    self.pending = None;
}

Check job.status() for LoadStatus::Failed(error) and show a useful error state. The host view must arrange notifications or polling while decoding. Dropping the job cancels publication of its result.

Once you have an image, build a normal styled element:

use gpui::{prelude::*, *};
use xgpui_media::image_view;

image_view(image.clone())
    .w(px(480.)).h(px(320.))
    .rounded(px(12.))

Clones share the source texture, so a thumbnail and a larger preview can reuse the same image. image_view stretches to the size you give it; match the source aspect ratio when you want to avoid distortion. PNG, JPEG and WebP first frames are supported. Loading from a URL and animated-image playback are not included.

Adjust an image without changing the original

For example, make an unselected thumbnail grayscale:

use xgpui_media::ImageFilter;

image_view(image.clone())
    .filter(ImageFilter::new().saturation(0.))
    .w(px(160.)).h(px(100.))

Or give a preview a small brightness and contrast adjustment:

let adjustments = ImageFilter::new()
    .brightness(1.05)
    .contrast(1.15);

image_view(image.clone())
    .filter(adjustments)
    .w(px(480.)).h(px(320.))

The GPU applies these adjustments while drawing. Changing a filter reuses the loaded source; it does not decode or upload the image again. Filters compose in call order and preserve alpha. They work on SDR ↗ sRGB colors. Blur, LUT grading, embedded color profiles, EXIF orientation and HDR ↗ handling are not implemented.

Set a loading budget for a scrolling gallery

Share a loader across related images. If loading competes with scrolling, you can limit how many new sources the renderer adopts in each scene:

use xgpui_media::{FrameUploadLimits, MediaLimits, UploadLimits};

let loader = MediaLoader::with_upload_policy(
    MediaLimits::default(),
    UploadLimits::default(),
    FrameUploadLimits { max_uploads: 1, ..Default::default() },
)?;

This example permits one new source per scene. Cached images still draw normally. The default frame byte limit is 64 MiB; an image's full mip chain must fit that limit. An oversized source reports an error, so resize it or raise the byte limit. A busy loader rejects new decode requests; keep a small application queue and retry as slots become available. This is not a promise that every frame will meet its timing budget on every machine.

Show frames from a camera or capture source

The producer supplies a VideoFrame; the view displays it. This is useful for a live preview where showing the newest available frame matters more than retaining old frames.

use xgpui_media::{VideoStream, video};

let (sender, stream) = VideoStream::channel();
// Keep stream in the view; give sender to your frame producer.
let preview = video(stream.clone()).w(px(640.)).h(px(360.));

// Producer: frame is a VideoFrame supplied by your capture/decoder adapter.
sender.publish(frame)?;

// UI: notify your view after changing playback state.
stream.set_playing(false);

The channel keeps one pending frame and one displayed frame. It does not open a movie file, decode video, play audio, seek, or synchronize playback. Native frame imports have ownership and synchronization requirements; see the adapter details below before integrating a producer. System playback adapters are tracked in issue #40.

Related: drawing a route or progress stroke

Trim and dash effects live in xgpui-svg, alongside the media work. A map route can use dashes; a progress indicator can reveal a fraction of a curve:

use gpui::px;
use xgpui_svg::path_effects::PathEffect;

let effect = PathEffect::new()
    .trim(0.0..0.65)?
    .dash(&[px(12.), px(6.)], px(0.))?;
let stroke = measured_path.stroke(&effect, px(3.))?;
// Paint the resulting GPUI path in a canvas: window.paint_path(stroke, color).

Here measured_path is a retained MeasuredPath built from your contours. Measure once, then change the effect as progress updates. See the contour effects guide for constructing and painting a path.

Further details

The following sections contain the resource contracts, platform-specific APIs and validation records for integration and review.

Loading and renderer details

Loading, ownership and bounds

  • PNG, JPEG and WebP first-frame decoding and CPU mip generation run on bounded native workers. Mips use area integration in linear sRGB with associated alpha, then return to the existing straight-alpha ↗ encoded-sRGB compositor contract. Odd dimensions and single-row/column sources retain their edge contributions.
  • MediaLimits bounds active jobs, encoded input bytes, per-image mip payload, and aggregate admitted payload. Admission rejects excess work immediately; there is no unbounded queue. Share one loader across related views.
  • Each job conservatively reserves max_image_bytes before decoding. The reservation follows image clones until the last snapshot drops. Unused reserved capacity is not reclaimed early. Defaults: two workers, 64 MiB/image and encoded input, 256 MiB aggregate admitted payload. Dimensions are at most 16384 on each axis and must fit the actual backend device limit.
  • These are source payload bounds, not a total process/VRAM guarantee. Encoded input, codec scratch, retained CPU pixels, GPU pixels and temporary padded staging buffers have separate costs. One GPU source is cached per image; switching device/queue/backend replaces that cache. In-flight/retained scenes may retain older GPU resources until normal scene/command release.
  • Dropping/cancelling a job suppresses publication. Cancellation is checked before decode and during mip generation; an active codec decode finishes before its worker slot and reservation can be released. try_take transfers an image once.
  • LoadStatus::Ready means CPU-ready. The first paint starts background GPU staging and returns a cached transparent 1x1 placeholder. Once staging completes, renderer preparation adopts the prepared resources and orders the upload before sampling. Retained renders and layout-size changes reuse the destination texture.
  • UploadLimits independently bounds active staging workers and accounted staging reservations. Defaults: two upload workers and 128 MiB staging. Metal/wgpu admission leases survive submission until GPU completion; D3D11 currently releases its reservation when submission is observed. A busy image reports Queued and retries on later paints without creating an unbounded task queue. A source larger than the entire staging budget reports Failed rather than remaining queued forever. Admission is not FIFO.
  • Staging accounting uses each mip's row size rounded up to 256 bytes. This matches Metal/wgpu buffer layouts; D3D11 driver allocation costs may differ. The staging reservation covers preparation and adoption. On Metal/wgpu both the image and GPU completion guard must release it; observing submission drops the image's reference, and the guard keeps it alive until completion. Dropping a pending image or abandoning an unsubmitted recording releases its references safely. A running worker releases its resources on return.
  • Metal/wgpu completion callbacks return exclusive buffers to a loader's queue-bound pool; a worker cannot refill one while the GPU may still copy it. Idle buffers are reusable only at the same total padded size. Idle mismatches are evicted when needed. staging_pool_stats() reports allocated/cached bytes, allocations and reuse counts; the current pool's byte capacity equals max_staging_bytes and includes borrowed as well as idle buffers.
  • GPU destination textures and driver overhead are not part of staging limits. Queue/device replacement can temporarily retain old in-flight resources along with the new pool. Shared admission still bounds outstanding staging leases; the pool's idle cache has its own capacity. These limits are not a hard total process/VRAM cap. Hidden retained images can hold staging references until painted, polled or dropped. There is no automatic visibility eviction.
  • Queue/device changes invalidate the cache and discard previous-generation worker results. Abandoned wgpu/D3D11 recordings can adopt the same staging resources again; there is no new pixel copy. retry_upload() invalidates an upload or retries a failure. Notify the host view after an explicit retry.

Backend contract and current limits

Native Metal and DirectX 11; enable feature wgpu for the portable renderer. The backend contexts expose additive create_image_output(&ImageTextureData) methods. Existing producer outputs still require the exact requested display extent. Image outputs explicitly opt into source-sized textures. Existing scene composition applies ordering, clipping, rounded coverage and inherited opacity.

Metal workers allocate private textures, fill exclusive shared staging buffers and record uncommitted blits inside an autorelease pool. An upload command's completion callback returns its buffer and releases admission ownership. wgpu workers fill exclusive mapped buffers; the host records copies and attaches resource/admission guards to the recording. Queue completion releases those guards. Abandoned wgpu recordings release guards without submission, leaving the staged source available for a retry. Mapping a reused wgpu buffer may wait for driver progress on the worker (bounded to five seconds), never on the UI preparation path.

D3D11 workers still initialize a one-use CPU staging texture and allocate the destination; the renderer records a deferred CopyResource. D3D11 does not yet pool these textures or claim GPU-completion accounting. Workers never submit or execute commands or access its immediate context. Native Windows validation is required before adding completion-driven D3D11 reuse.

For wgpu/D3D11, image_upload_context().stage(data) remains the unpooled API and adopt_image_upload(staged) records the handoff. wgpu also offers queue-bound staging_pool / stage_with_pool and completion-guarded adoption. Metal provides stage_image_upload_with_pool. Existing synchronous convenience APIs remain available. xgpui-media uses the pools for full Metal/wgpu sources and allocates only a tiny placeholder during preparation.

image.upload_status() reports Idle → Queued/Preparing → Staged → Uploading → Ready, or Failed(error). Ready means host-submitted, with queue ordering before sampling; it does not assert GPU completion. image_view and MediaImage::paint request redraws until ready or failed. A caller that inserts raw CustomDraw records must drive repaint/status polling itself, including headless tests. Empty, fully clipped and zero-opacity media paint calls do not start uploads or request loading redraws. CPU job loading still requires host notification/polling as described above. Use loader.upload_stats() to inspect active jobs and outstanding staging reservations.

Per-frame admission

MediaLoader::with_upload_policy(media_limits, upload_limits, frame_limits) adds FrameUploadLimits independently of decode and staging admission. Defaults are at most two newly adopted sources and 64 MiB of unpadded mip payload per scene frame. All images sharing a loader share this budget. Cached source draws and the 1x1 placeholder do not spend it; duplicate placements reuse the first adoption. When exhausted, prepared images stay Staged, display their placeholder and try again next frame. The byte/count counters reset on the next scene preparation.

GPUI's additive CustomContent::prepare_in_frame passes a shared PreparationFrame; its default forwards to the previous request-aware method. The window geometry adapter preserves both logical coordinates and this context. Direct low-level prepare calls get an independent one-call frame; custom wrappers should forward prepare_in_frame to preserve scene-wide admission.

A source must fit the configured frame byte limit in full. Larger sources report Failed before worker allocation, rather than being queued forever or silently exceeding the cap. Raise the limit or use a smaller source. Chunked mip uploads, per-frame time limits, priority/FIFO fairness and GPU timestamp measurement remain follow-ups. The release benchmark below measures CPU work and staging reuse. Pooling is a bounded cache, not a fixed two-buffer ring. There is no zero-stutter or frame-rate guarantee.

SDR sRGB input only. Embedded ICC ↗, EXIF orientation and HDR interpretation are not implemented. Mip generation is alpha-aware; the existing compositor still samples straight encoded channels between texels/mip levels. This is not a fully linear, premultiplied ↗ image-compositing pipeline.

Upload status example

use xgpui_media::{MediaLoader, MediaLimits, UploadLimits, FrameUploadLimits, UploadStatus};

let loader = MediaLoader::with_upload_policy(
    MediaLimits::default(),
    UploadLimits { max_jobs: 2, max_staging_bytes: 128 * 1024 * 1024 },
    FrameUploadLimits { max_uploads: 2, max_bytes: 64 * 1024 * 1024 },
)?;
// After taking a CPU-ready MediaImage from its ImageJob and painting it:
match image.upload_status() {
    UploadStatus::Ready => { /* commands submitted; source can be sampled */ }
    UploadStatus::Failed(error) => { /* show error; offer image.retry_upload() */ }
    _ => { /* placeholder / staging / host handoff pending */ }
}
let staging = loader.upload_stats();
let cache = loader.staging_pool_stats();

Image color filters

use xgpui_media::{image_view, ImageFilter};
let filter = ImageFilter::new()
    .brightness(1.05)
    .contrast(1.15)
    .saturation(1.3)
    .hue_rotate(15.)
    .tint([1., 0.7, 0.3, 0.1]);
let element = image_view(image.clone()).filter(filter).w(px(640.)).h(px(400.));
// Low-level painting:
image.paint_filtered(window, bounds, radii, filter);
// Independent replayable custom content using the same retained source:
let placement = image.filtered(filter);

Each filter chain compiles to three affine RGB rows. Metal, wgpu and native D3D11 apply the rows after texture sampling, before native coverage and inherited opacity. No extra render target, pass, decode or source upload is introduced. Different placements may use different filters while sharing the same image cache. The default is identity; existing image and custom-content callers keep their current output. This API applies to SDR media, not wide-color native backgrounds.

Adjustments operate on encoded sRGB channels; mip generation still operates in linear light. Operations compose in call order. Brightness multiplies RGB; contrast uses a 0.5 pivot; saturation uses Rec.709 luminance coefficients; hue rotation is in degrees; tint mixes toward its RGB by its fourth component and preserves source alpha. RGB clips to the SDR target range after the combined transform, rather than between operations. These are color adjustments, not ICC color management.

Factors clamp to 0..8, nonfinite factors use identity, and nonfinite hue uses zero. Tint components clamp to 0..1 (nonfinite becomes zero). A composition that overflows is ignored. Blur and LUT grading remain pending.

The media lab has five filter controls and Reset filters. Only the right panel is filtered, so the left remains a source reference. Watch the upload counter while changing filters: it should stay at one. Append --vivid to ui or a headless run to start with combined brightness, contrast and saturation adjustments:

GPUI public API changes: additions and compatibility

GPUI API additions cover ImageTextureData, image output constructors and trilinear compositor sampling. Existing ordinary custom outputs still require display-sized extents; no public scene struct layout or existing method signature changes in this slice.

Native video adapters and ownership

Video snapshots — first native slice

VideoStream, VideoSender, VideoFrame, video and video_frame separate frame production from presentation. The portable channel retains one pending frame and one displayed frame, replacing obsolete pending work instead of building a FIFO. Native GPU in-flight references have separate lifetimes; this is not a total memory budget or a playback clock. Source timestamps are metadata. The channel itself has no decoding, audio sync or seeking. System playback adapters are separate follow-up work outside the GPU surface scope.

use xgpui_media::{VideoStream, VideoFrame, video};
let (sender, stream) = VideoStream::channel();
// Retain stream in your view and move sender to your frame producer.
let viewport = video(stream.clone()).w(px(640.)).h(px(360.)).rounded(px(16.));
// Producer: sender.publish(frame)?;
// UI controls: stream.set_playing(false); cx.notify();
// Resume selects the newest pending frame, rather than playing old frames.

The live element requests animation frames while visible, playing and open. Paused, closed, empty, fully clipped and zero-opacity viewports request none. The host must notify its view after changing presentation state; paused/closed elements do not subscribe to background wakeups. Closing/dropping the sender retains the final frame. Dropping the last stream consumer closes admission and releases channel-held snapshots. snapshot() observes pending content when playing; stats() reports published, superseded-before-observation, observed, pending, closed and playing state. Observed counts are host snapshots, not GPU completion or presentation fences. Multiple stream clones share pause/display state. For consistent duplicate placements, capture once in your render and use video_frame(snapshot.clone()) in each viewport. video_frame itself does not request redraws.

macOS BGRA / IOSurface import

use xgpui_media::{CoreVideoFrame, VideoFrame};
// pixel_buffer comes from an external producer/decoder. It must be IOSurface and
// Metal compatible, with completed writes and opaque or straight-alpha BGRA8.
// SAFETY: the producer cannot write/recycle it while any snapshot clone exists.
let native = unsafe { CoreVideoFrame::from_bgra(pixel_buffer)? };
let frame = VideoFrame::core_video(native, source_timestamp);
sender.publish(frame)?;

Native Metal creates a BGRA texture view of the retained pixel buffer: no CPU pixel readback, image staging upload or display-sized intermediate is used. Each snapshot caches up to four queue-bound imports and reuses the view on resize/replay. Import failures and unsupported formats return errors. The renderer retains producer snapshots, pixel buffers and legacy CoreVideo views until sampling completion, including when a scene is replaced before the GPU finishes. Construction is unsafe because external pixel-buffer mutation and producer synchronization cannot be proved by a retained reference alone. Premultiplied alpha, orientation transforms, HDR metadata/color management and transfer conversion remain pending. The new element also supports explicit SDR NV12 conversion as described below.

macOS NV12 — direct two-plane sampling

use xgpui_media::{CoreVideoFrame, Nv12Matrix, VideoFrame};
// SAFETY: initialized, synchronized, immutable IOSurface/Metal-compatible NV12;
// matching SDR matrix and centered chroma. The producer cannot recycle this frame.
let native = unsafe { CoreVideoFrame::from_nv12(pixel_buffer, Nv12Matrix::Bt709)? };
sender.publish(VideoFrame::core_video(native, source_timestamp))?;

from_nv12 accepts opaque 8-bit CoreVideo 420f (full range) and 420v (video range), with even dimensions and matching Y / interleaved CbCr planes. The pixel format selects range; Nv12Matrix::Bt601 or Bt709 explicitly selects coefficients. No matrix inference from attachments is performed. Use the matrix matching the producer and centered chroma. Other chroma locations, 10-bit/P010, BT.2020 and HDR are outside this API. Matrix conversion preserves the source encoded RGB transfer; it does not perform transfer-function ↗, gamut ↗, primaries or HDR color management.

CoreVideo imports R8 luma and RG8 chroma texture views. The same compositor fragment samples both planes and converts YCbCr to encoded SDR RGB before the normal image color transform, opacity, clipping and rounded coverage. Conversion adds no image staging upload, CPU readback, offscreen conversion target or extra render pass. Source planes, CoreVideo wrappers and the immutable producer remain retained through GPU completion. Resize and duplicate placements reuse the same queue import. The public MetalCustomOutput fields and generic producer format contract are unchanged; native NV12 uses a separate checked internal output.

Release captures with Metal API validation check BGRA and all four NV12 matrix / range combinations. Every mode checks all four color bars, clipping, rounded coverage, opacity and source reuse after resize. Fixed quantized midtone vectors and neutral black/white endpoints check conversion coefficients/ranges separately from the fixture generator. Native lifetime tests cover BGRA and all four NV12 combinations through sampling completion. The release UI has been exercised for format cycling, pause/resume, replacement bursts, opacity, corners, stop and restart.

The existing paint_surface path now also accepts BGRA, while its NV12 full-range behavior remains covered by a regression. Unsupported formats return an error instead of triggering the previous format assertion; error paths end active Metal encoders cleanly. Legacy PaintSurface fields and paint_surface signatures are unchanged. Use the new styled element for rounded corners and inherited opacity.

VideoFrame::new is an advanced adapter for existing custom producers that return source-sized backend outputs. It does not implement DXGI or DMA-BUF import. The video lab currently requires macOS Metal. A Windows native constructor is described below. Linux has an initial Vulkan DMA-BUF snapshot adapter described below; full synchronization/import negotiation remains pending. Windows cross-compilation covers the portable API and initial BGRA adapter; the interactive synthetic source remains macOS-only.

Windows BGRA surfaces — initial adapter

DxgiFrame (re-exported by xgpui-media on Windows) retains a native ID3D11Texture2D. VideoFrame::dxgi(frame, timestamp) feeds the same bounded channel and styled video element. Import creates native views and samples the original texture, without CPU readback, staging upload or a display-sized copy.

The unsafe DxgiFrame::from_bgra constructor accepts only dedicated BGRA8 UNORM, default-usage, shader-readable render targets with one mip, one array slice and no multisampling. Preparation rejects a texture from another device. Producer writes must be synchronized before presentation; pixels must remain immutable throughout the native resource lifetime, including references held by queued D3D11 commands. Dropping a Rust frame is not a pool-recycle signal. The direct constructor rejects keyed-mutex resources; use the shared-handle constructor below for those. Device negotiation, decoder array slices and YUV conversion remain unsupported.

Windows native BGRA lab presentation and just lab-test passed in owner testing on 2026-11-04. A separate Windows-only WARP library regression covers native resource identity (no copy), retained pixels, resize-independent source extent, wrong backend/device and unsupported format rejection; execution of that dedicated suite is not established by the same-device lab result; see Windows validation. Linux DMA-BUF runtime verification, explicit fences/pool reuse and broader surface formats remain required before Phase 5 is complete.

System file playback is tracked separately in issue #40. The surface lab generates frames itself and requires no video file.

Keyed DXGI shared snapshots

unsafe DxgiFrame::try_from_shared_bgra(&host_device, nt_handle.as_handle(), ready_key, release_key) opens an NT shared handle on the renderer's D3D11 device. Supply the host device (the device exposed by Dx11CustomContext), not an unrelated producer device. The handle is borrowed for open only; the imported COM texture retains the native allocation after the handle closes. Legacy DXGI handles are not accepted.

The surface must satisfy the BGRA descriptor restrictions above and expose a keyed mutex. The producer writes under its key and releases with ready_key. Acquisition uses timeout zero: Ok(None) means busy, so retain the previous snapshot and retry later; it never waits for the producer. Only exact S_OK grants ownership. DXGI timeout is distinct from abandoned ownership, which returns an error requiring surface recreation. Producer and consumer keys must differ.

A successful frame owns a shared read lease. Frame clones and prepared compositor outputs keep that lease alive. The last reference releases with release_key after referring command lists have been submitted or discarded; DXGI provides the GPU ownership handoff. The producer may write again only after acquiring that key. Merely dropping the producer's published frame handle is not sufficient: the video channel's last displayed snapshot may still hold it. Use multiple shared allocations for a progressing stream; do not wait on the UI thread for the currently displayed allocation. All native aliases must obey this protocol. A failed release is logged; a lost/abandoned device or resource must be recreated. This API supplies snapshots, not a decoder, media clock or generic mutable surface.

The Windows-only shared-surface regression uses separate WARP devices, tests busy acquisition and borrowed-handle closure, verifies clones/prepared outputs delay producer access, renders the shared pixels through the compositor, then checks producer-key handoff and captured color. The tests compile from macOS but have not yet been executed on Windows. On a Windows SDK host, run in release mode:

just --justfile apps/xgpui-ext-lab/media-lab/justfile dxgi-test

See Microsoft's AcquireSync contract, ReleaseSync contract and NT-handle import API.

Linux DMA-BUF snapshots — initial Vulkan adapter

With xgpui-media's wgpu feature, DmaBufLayout, DmaBufFrame and VideoFrame::dma_buf provide an opt-in native snapshot path. This enables gpui-wgpu/dma-buf. On Linux, device creation requests wgpu's external DMA-BUF capability only when the adapter advertises it. Existing GLES/fallback rendering still works; DMA-BUF import reports unsupported instead of uploading CPU pixels. DmaBufFrame::supported_by(&context) checks the basic host capability before an application attempts import. A specific allocation can still be rejected by the driver. This does not negotiate a producer's device or layout.

use xgpui_media::{DmaBufFrame, DmaBufLayout, VideoFrame};
let layout = DmaBufLayout::linear_bgra(source_size, stride, offset, drm_modifier)?;
// SAFETY: dedicated, initialized, immutable BGRA allocation; producer fence and
// matching Vulkan EXTERNAL/GENERAL release have already completed.
let snapshot = unsafe { DmaBufFrame::from_bgra(owned_dma_buf_fd, layout) };
sender.publish(VideoFrame::dma_buf(snapshot, source_timestamp))?;

The initial contract accepts exactly one linear DRM_FORMAT_ARGB8888 plane (little-endian BGRA bytes), opaque or straight alpha. Explicit modifier zero, aligned row stride/offset, dimensions 1..16384 and a 256 MiB layout ceiling are validated. Device limits are checked at import. Tiled/implicit modifiers, YUV, multiple planes and premultiplied alpha are excluded.

The unsafe constructor transfers an OwnedFd. It must be a real DMA-BUF matching the supplied metadata and backed by a compatible allocation on the same physical GPU/driver. Producer writes and its fence must have completed. This slice accepts Vulkan exports released to VK_QUEUE_FAMILY_EXTERNAL in GENERAL layout; GBM/EGL allocations requiring FOREIGN_EXT ownership are outside this contract. It does not import/wait for a sync-file fence, perform a CPU wait, return a release fence, or signal that a pool allocation may be recycled. Pixels must stay immutable for the allocation's entire native lifetime, including GPU references after the Rust frame drops. Use dedicated snapshots; mutable decoder pools are unsupported.

Preparation duplicates the FD and lets Vulkan consume that duplicate, preserving the frame's original FD for import retry after an abandoned preparation. It records the external queue-family acquire on the host preparation encoder, preserving GENERAL. A completion guard retains that raw-barrier resource even if the main render fails before tracked sampling; wgpu then tracks the normal shader-read layout transition. Existing pixels are retained rather than treated as uninitialized storage. One host queue owns the cached import. Repeated placements/resizes reuse it; a different queue is rejected. No CPU readback, image staging upload, or display-sized copy is performed. The imported native memory retains its payload through GPU resource lifetime.

The Linux implementation and media API are cross-checked from macOS. Release host tests validate padded rows/offsets and rejection of invalid dimensions, alignment, modifiers, overflow and excessive layout sizes. These tests do not exercise a Linux GPU. Native FD import, validation-layer synchronization and pixel capture remain unverified until run on a compatible Linux Vulkan host. Phase 5 remains incomplete. The existing interactive synthetic source is still macOS-only.

The native recipe selects Metal on macOS; the portable recipe enables wgpu. Debug builds are rejected. For custom output paths, invoke the lab with --headless --upload-bench --bench-report PATH --png PATH (plus --wgpu / --features wgpu for portable).

The workload uses six deterministic noisy 2048×2048 PNGs with solid center markers, full mip chains (about 128 MiB retained source payload), and twelve placements in a 900×600 scene. It warms the pipeline/target with a small source, decodes/mips all full sources before timing, then stages three waves by invalidating each source cache between waves. Admission allows two upload workers, 64 MiB staging, and one source / 32 MiB payload per scene frame. The scene is paced at roughly 60 Hz. A final 120-frame phase renders the same full-source scene from cache.

The JSON stores every frame's render_scene CPU wall duration and summed source preparation duration, plus nearest-rank p50/p95/p99/max and sample counts. It also records decode/mip wall time separately, observed newly submitted sources and staging peaks, pool allocations/reuses, per-source upload counts, backend/build metadata and interpretation caveats. Assertions check per-frame admission, drain and timeout behavior, all source submissions, reuse bounds and both placements' final colors. Final render-target readback validates pixels outside timing.

These timings exclude PNG generation, pipeline warmup, decode/mips, pacing sleep and final readback. They are not GPU timestamps, whole-window frame times or a zero-stutter guarantee. Driver backpressure can affect CPU time; instrumentation and background system load also matter. Upload-phase samples include placeholder, staging and adoption frames, so compare sample counts and raw frames rather than assuming each sample is an upload duration. Observed staging drain includes frame pacing/polling and backend lifetime semantics; Ready alone means host-submitted. Source/staging accounting is not a total process-memory or VRAM measurement.
