Releasing XGPUI

This is the authoritative release guide. Historical publication evidence is kept in the publication archive; release-specific reviews live in release-reviews/.

A release starts as a release issue that shows the whole plan in one place: what changed, every crate's next version and why, the release notes and the remaining steps. Everything that changes the repository then lands through reviewed PRs. The owner makes the decisions and does the two irreversible steps by hand: publishing the crates and deploying the website.

The issue's checklist tracks these steps; the agent ticks items as their PRs merge. #338 (XGPUI 4.1.0) is the first release made this way. Use it as the reference for the next one: its description shows the expected layout, and its Lessons learned section is folded into the rules below.

1. Release issue — agent

When the owner asks for a release, open an issue titled Release: <headline versions> — <main changes>. Change nothing in the repository in this step.

  • Baseline: the most recent completed release tag (see Release records). Exclude unfinished or superseded tags.
  • Candidate: current main, recorded by commit. If anything merges to main before the tag is created, re-run the review and update the issue.
  • Changes: list every merged PR since the baseline and group the packaged changes by crate. Distinguish source changes from README, manifest and test-only changes; only packaged content needs a version.
  • Versions: run the read-only release-check against the baseline as an input, then give every crate a next version and a reason under the versioning policy. Show breaking changes and the re-exports that carry them into dependents.
  • Re-exports and pins, by hand: release-check doesn't see a crate whose own code is unchanged but whose pinned dependency takes a breaking bump. On #338 it reported xgpui-gamut unchanged, yet gamut re-exports xgpui-color, so color's breaking release forced gamut 0.5.0. List every internal requirement the new versions no longer satisfy, and every pub use of another XGPUI crate.
  • Dependency pins: list each internal requirement that must rise, and why.
  • Packaged READMEs: compare every crate README's install snippet with the new versions. READMEs ship in the package and drift; #338 found four snippets naming versions from earlier releases.
  • Downstream check (recommended): build xgpui-luma against the candidate with a local, uncommitted .cargo/config.toml that patches every XGPUI crate to this checkout, then run its lab tests. Record what breaks and what had to change. On #338 this found two native paragraph bugs (fixed in #336) and eight API breaks before anything was published.
  • Release notes (draft): highlights, migration notes per breaking crate, the core public API changes with the PRs that approved them, and verification so far.
  • Publish order: every crate to publish, in dependency order with its new version, computed from Cargo metadata.
  • Checklist: the remaining steps in this guide, plus any release-specific PRs. The issue ends with a Lessons learned section, filled in after the release (see step 7).

Questions the policy can't settle (for example, whether a technically breaking change in a core crate takes a major or a minor version) go in a **Decision needed** section with the options and a recommendation.

2. Decisions — owner

Answer the issue's open decisions. The agent records each answer in the issue and ticks it off.

3. Release PRs — agent, owner merges

Work under issue-<N>/epic, one PR per concern, each into the epic. GitHub deletes the epic branch when it merges, so a follow-up after that recreates issue-<N>/epic from main.

  • Versions and pins: crate manifests, dependency requirements (including the labs' manifests for breaking versions), scripts/release-packages.json, packaged README install snippets and Cargo.lock. Before opening it, build-manifests --check must pass and release-check must report every changed crate ready-for-new-version with no pin problems.
  • Website docs: pages/ updated for the coming versions: What's new, crate pages, guides for new APIs, and the homepage's Start here subtitles. Leave the changes uncommitted until the owner has hosted them locally (just pages-serve) and approved them. What's new can't name the release tag, which is created on the commit that contains it; link the release issue and the GitHub releases list instead. Merged, not deployed.
  • Records: a review file in docs/release-reviews/ when the release needs more evidence than the issue holds, and any guide changes.

Then open the epic's PR into main. CI must pass, with one exception. A macOS job cancelled after its queue timeout, with no runner and no steps, is an infrastructure failure rather than a test result; it happened on #334, #337 and #343. Re-queue it, run its steps locally on the same commit, or let the owner waive it, and say which in the PR. The owner tests Windows and Linux by hand only once changes are on main.

The owner merges into main. The repository doesn't allow auto-merge, and the agent isn't woken when CI succeeds, so the owner tells the agent to merge once CI is green. The agent re-checks every result before merging.

4. Tag and draft record — agent

On the merged commit, before any upload:

  • Create the remote tag release-YYYY-MM-DD-COMMIT (the commit's UTC date and its first 12 hex characters) and verify that it resolves to the full commit SHA. Each distinct commit gets its own tag; a retry of the same release reuses it.
  • Create a draft GitHub release on that tag with the issue's title, notes and old → new version table. Keep a copy of the title and body; the registry workflow's finalizer overwrites them if it runs.
  • Add the tag and the draft's link to the issue.

5. Publish crates — owner

From a clean checkout of the tag, with CARGO_REGISTRY_TOKEN set:

git switch --detach release-YYYY-MM-DD-COMMIT
just release-preflight   # registry plan; no uploads
just release-check       # package and build check; no uploads
just release-publish     # uploads in dependency order

Each step requires the previous step's report for the same tag. Reports are kept in ../xgpui-release-artifacts/<commit>/. release-publish skips versions already on crates.io with identical contents, verifies each upload before its dependents proceed, and stops on an unknown upload outcome.

On failure: keep the tag and draft. Retry the same tag where it's safe; verified uploads are skipped. Never change an uploaded version's contents or move its tag. A source fix needs a repair PR, a new commit, a new tag and a new draft. Mark the old draft superseded and keep its tag.

6. Finish the record — agent

After the owner reports the publish:

  • Read the publish report. Every crate must be published-verified or already-published with a registry checksum, and the source SHA must match the tag.
  • Check the release from a fresh consumer outside the checkout: exact versions from crates.io, no repository patches or credentials, building code that uses the new APIs. State the host and what it doesn't cover.
  • Restore the reviewed notes in the draft, append the verification table and the consumer result, then publish the draft and recheck the tag SHA.
  • Tick the issue's checklist.

7. Deploy the website — owner

Run the Publish documentation workflow (pages.yml) manually on main, then tell the agent. On #338 "deployed" was reported before any run existed, so before closing the issue the agent confirms all of these:

  • a Publish documentation run on the release commit succeeded;
  • the latest github-pages deployment is that commit;
  • the live pages carry the new content (What's new, the homepage and the changed guides);
  • both gallery Wasm bundles are served.

Then the agent adds the deployment link to the release record and the issue, and writes the issue's Lessons learned section: what worked, what caused friction, and suggested changes for the owner to decide. Anything durable goes back into this guide in a docs PR. Close the issue.

Versioning policy

  • Patch: compatible fixes, internal backend changes, packaged documentation and compatible dependency updates.
  • Minor: new capabilities that preserve supported public APIs.
  • Major: deliberate breaking changes to supported public APIs.
  • Before 1.0: use a minor bump for breaking changes or new capabilities; use a patch for compatible fixes, internal changes and packaged docs. State whether a minor release contains breaking changes.
  • Dependent crates: bump only when packaged content or dependency requirements change. Do not automatically propagate a major bump; review whether changed dependency types affect the crate's public API. A crate that re-exports a dependency inherits that dependency's breaking changes.
  • Internal requirements: use full stable compatible requirements (for example, 3.0.0 or 0.4.0) for XGPUI libraries. Preserve an existing minimum when it admits the candidate version; raise it when code needs a newer API or fix. Release preparation must not raise compatible minimums just because a dependency releases. Exact requirements remain appropriate in registry verification fixtures. Upstream helper pins remain unchanged. Release tools support full stable caret/default, tilde and exact requirements; other syntax requires explicit review.
  • Compatibility review: inspect removed or renamed APIs, signatures, #[non_exhaustive] and exhaustive enum variants, features and minimum supported Rust version. Explain their impact and the proposed version in the issue.
  • Exceptions: need the owner's decision on the issue, recorded with the compatibility impact in the release notes.

Every changed crate needs a version rationale. Automated checks inform the review; they don't assign versions.

Public API additions and changes in non-extension GPUI crates are reviewed and approved individually in their own PRs (see AGENTS.md). The release issue lists them with links to those approvals.

Documentation-only publishing

Website fixes and improvements can ship without a crate release, tag or version bump: merge the pages/ change, then the owner runs the Pages workflow. Keep the website accurate for currently published crates and don't announce unreleased APIs as available. A docs-only deployment is not a new release baseline.

Documentation inside a published crate archive is different: shipping its updated contents requires a new crate version.

Release records

The GitHub release is the durable record, and release-check reads past releases to find the baseline. Keep the human notes and the old → new table, and append a separate three-column table containing every mapped crate and its actual result:

| Crate | Version | Result |
| --- | --- | --- |
| `crate-name` | VERSION | published-verified |
| `unchanged-crate` | VERSION | already-published |

The history checker recognizes exactly published-verified and already-published in the third column. Prose or an old/new version table alone is not enough. Mark abandoned partial releases incomplete or superseded, keeping their tags and publication results; never use them as a baseline.

The maintenance/Parley release shows a complete record: 15 verified new versions, 2 verified skips, a registry-only consumer, and the full notes with the verification table.

Tools

Release tooling and its regression tests live in tools/release-sync and run through just test on every host. The version source of truth is scripts/release-packages.json; don't keep a second current-version table elsewhere.

# Read-only: changed packages, versions and pins against a baseline and crates.io.
cargo run --locked --manifest-path tools/release-sync/Cargo.toml -- release-check --epoch LAST_COMPLETED_RELEASE_TAG --report ../xgpui-release-artifacts/release-check.json

# The generated root manifest is current.
cargo run --locked --manifest-path tools/release-sync/Cargo.toml -- build-manifests --check

# The release-tooling suite only.
just test --only release-sync

release-check needs registry access but uploads nothing, and it doesn't compile or test code. Pass the baseline explicitly: the history parser recognizes only the verification table above, and a missed baseline can falsely flag unchanged crates.

The owner's publish commands (just release-preflight, release-check, release-publish) wrap registry-release in its plan, dry-run and publish modes:

  • plan inspects candidate archives and registry versions, reporting publish-needed, already-published or version-conflict. Changed packaged contents under an existing version fail the plan.
  • dry-run also performs registry-backed package and build verification where dependencies are available. Dependents of unpublished candidates are verified during publishing.
  • publish requires the publish FULL_COMMIT_SHA confirmation, which the just recipe supplies from the tag, and CARGO_REGISTRY_TOKEN.

Existing versions are skipped only after comparing packaged source and normalized manifests. Generated lockfiles, VCS metadata and publication permissions are excluded from that comparison; source, resources, README, features and dependency requirements remain significant.

Known gaps

These are known holes in the tooling. Cover them by hand until they're fixed:

  • release-check doesn't flag a crate whose pinned dependency takes a breaking bump, or one that re-exports such a dependency.
  • No check compares packaged README install snippets with scripts/release-packages.json.
  • just pages-check doesn't check relative links in docs/*.md.
  • scripts/fixtures/native-package-consumer pins old exact versions. Step 6's fresh consumer replaces it for now.

Validation

Before the release PRs merge:

just test
just pages-check
git diff --check

just test runs the current host's suites. Use just test --list to inspect coverage, or just test --only native-libraries to isolate a failure. CI covers macOS, Linux and Windows for every PR; the owner's manual Windows and Linux checks happen on main. Use the labs (just labs) for graphical checks. just pages-check checks the static website in pages/, which is edited by hand. Toolchain and host prerequisites are in Local development.

Upstream release imports

gpui-unofficial is xgpui's upstream. main contains xgpui's maintained code. Sync prepares an incoming tree proposal, not an integrated or buildable update.

Review a release

Imports run locally on an issue epic, as #284 did for 1.28.1. Build the tool, then compare a release with xgpui's current tree:

cargo build --locked --release --manifest-path tools/release-sync/Cargo.toml --target-dir target/release-sync
tool=target/release-sync/release/xgpui-release
$tool review prepare --release RELEASE --snapshot target/incoming --report target/review.json \
  --normalizer "$tool" --map scripts/crate-names.json   # optional: --expected-sha FULL_SHA
cargo run --locked --manifest-path tools/release-sync/Cargo.toml -- context --report target/review.json \
  --output target/zed-context.md --json-output target/zed-context.json

On a fresh review branch, apply the differences with $tool review code, review cargo and review metadata (each with --snapshot target/incoming --report target/review.json), committing after each. $tool review-notes --report target/review.json --context target/zed-context.md --output review.md writes the PR description.

The proposal uses separate commits:

  1. Code: changed source, shaders, build scripts, assets and other package files, including additions and deletions.
  2. Cargo versions/dependencies: package versions and dependency requirements, which affect dependency resolution.
  3. Generated metadata/artifacts: generated package READMEs, provenance and other retained capture metadata.

Release context uses the exact old/new Zed SHAs in snapshot provenance, never latest-release or previous-stable guesses. Its path filter is the union of both captures' transform-metadata.json crate inventories, including nested crates. It links relevant Zed commits and referenced PRs, with root Cargo dependency changes and unrelated range commits labeled separately. Missing provenance, incomplete API pagination and non-forward ranges fail context generation rather than silently reporting no changes. The Markdown/JSON context accompanies the PR; no issue or comment is created in the upstream repository.

The PR links each commit and lists code differences separately. A release with no differences needs no PR.

Sync also compares a clean snapshot of the previously recorded source release. This labels whether each proposed file changed upstream and whether xgpui has a local modification. It does not automatically merge or resolve those overlaps. A downstream-only code difference is reported and retained, not applied. When upstream also changed a file, its incoming version is a manual review proposal: combine or reject overlapping changes before any merge.

main remains untouched. Complete incoming versions are placed only on the review branch. Platform validation, integration, publishing and merging are separate work.

For example, 1.25.3 contains release metadata changes and no upstream Rust source changes relative to 1.25.2. The spring clock difference against xgpui is a local patch, not an upstream fix; it is retained with its regression assertion.

Names and provenance

For example, gpui-unofficial becomes gpui, and gpui-linux-gpui-unofficial becomes gpui-linux. Rust dependency aliases such as gpui_linux stay as they were. Cargo package identities, dependency references, directory paths and local overrides change together. The unused nested transformed-crates staging mirror is excluded from imports and removed by normalization. Required per-crate vendored sources are preserved.

upstream.json retains the source repository, release and commit, plus Zed's reported provenance. source_packages retains original names/paths; packages describes the local normalized tree. normalization records the schema and name map. registry_packages records the supporting crates fetched from the matching published gpui-unofficial release. Retained local crates preserve upstream repository URLs, Rust source, licenses and READMEs.

Package names change for downstream consumers. Existing dependency aliases can stay, but their package and path fields must point at the normalized names. Local directory names remain stable. scripts/release-packages.json maps the maintained packages to downstream xgpui-* identities at 1.0.0 for the framework and 0.2.0 for extensions; upstream.json records those separately under distribution. Upstream helper versions continue to follow the captured release.

Integrate and validate

Review and resolve the incoming proposal on a development/integration branch. Preserve local Rust edits when resolving conflicts; do not replace main's capture with a fresh generated snapshot as a substitute for merging. The first normalization is a directory/package migration; later releases use the same stable paths.

After integration, run from the repository root. The local-source patches live in the root workspace manifest, so the standalone tools' lockfiles don't record them and need no refresh when captured versions change:

cargo run --locked --manifest-path tools/release-sync/Cargo.toml -- normalize --check
cargo run --locked --manifest-path tools/release-sync/Cargo.toml -- build-manifests
cargo check
cargo build --locked

cargo test --locked --manifest-path tools/release-sync/Cargo.toml
cargo run --locked --manifest-path tools/release-sync/Cargo.toml -- build-manifests --check

build-manifests reads the package map and preserves native target selection, standalone workspace exclusions and the compatibility patches. It supersedes the removed Python update_build.py compatibility entry point. Review and retain the root lockfile.

Supporting crates listed in scripts/registry-crates.json resolve from crates.io at the captured release version. Only the retained framework/backend crates are locally overridden; see build details.

For standalone checks, continue invoking Cargo from the repository root so it discovers .cargo/config.toml (the shared target directory). The captured crates are root workspace members, so the root manifest's local-source patches apply. For example, on macOS:

cargo check --config .cargo/validation.toml \
  --manifest-path gpui/crates/gpui-platform/Cargo.toml \
  --features font-kit,runtime_shaders
cargo test --config .cargo/validation.toml \
  --manifest-path gpui/crates/gpui/Cargo.toml --lib \
  --features gpui_platform/runtime_shaders

.cargo/validation.toml remains separate from generated capture overrides. It restores the Proptest and async-process Git revisions needed by this release. Cargo patches do not force a lower version over a newer compatible registry version; inspect metadata when updating versions. A separate consumer must carry its own local package overrides rather than assuming this checkout's config is inherited.

Review the website in pages/ after each release; just pages-check catches broken links and a stale upstream baseline, not stale narrative.

The review branch is an unintegrated proposal with no platform validation; review and test the chosen integration separately.

How imports and builds stay separate

The captured manifests each declare their own workspace. The root workspace explicitly excludes each of those directories and builds their libraries as path dependencies. The harness does not rewrite their manifests or source. A separate downstream spring-animation fix uses the scheduler clock so headless tests advance deterministically; the clean upstream branch retains the original. The unused nested transformed-crates staging mirror is removed during import and normalization. Required per-crate vendored shader inputs remain intact.

Cargo.toml and tools/build-all/Cargo.toml are generated development files; they are not overwritten by upstream imports or downstream normalization. After an import adds or removes packages, regenerate them and update the root lockfile on the development or integration branch:

cargo run --locked --manifest-path tools/release-sync/Cargo.toml -- build-manifests
cargo generate-lockfile
cargo build --locked

CI checks xgpui-release build-manifests --check to detect a stale harness. cargo run --locked --manifest-path tools/release-sync/Cargo.toml -- build-manifests --check delegates to the same Rust generator. Review its platform classification when upstream adds a backend. Keep the root Cargo.lock committed for reproducible native builds.

The generated root manifest restores production compatibility dependencies from .cargo/validation.toml. The Proptest override stays scoped to explicit standalone test validation, avoiding an unused-patch warning in root library builds. Compiling the macOS utility crate requires Zed's async-process fork: its process launcher calls Child::adopt_raw_pid, which the registry dependency does not provide. The fork revision is taken from the original Zed release's workspace patch. These overrides repair extraction omissions without editing captured source.

The local Apple backends and extension producers use objc2, objc2-metal, and block2. The legacy Cocoa/metal-rs block compatibility patch is no longer needed by this checkout. Published versions can still resolve the older bindings; verify a consumer's selected dependency graph independently of local builds.

Local naming

The raw gpui-unofficial release remains on upstream. Development uses a normalized capture with names such as gpui and gpui-linux. The Rust tool in tools/release-sync applies scripts/crate-names.json and preserves original package paths in upstream.json. See the sync process.

Published supporting dependencies

scripts/registry-crates.json maps former local helper names to their published *-gpui-unofficial packages. Normalization preserves Rust dependency aliases, features, target conditions, and upstream source provenance. It removes helper source directories and local patches, and records registry identities and the release version in upstream.json. Core, macros, and platform/renderer backends remain local. Runtime Rust source is not rewritten by this migration.

After an upstream import, run normalization before generating build manifests. Normalization also updates direct helper dependencies in app and extension manifests. Refresh their lockfiles when changing the captured release. The registry version follows the captured core manifest, not the latest registry release. Keep shared types such as Refineable on the same registry package throughout the graph.

Verify resolved package identities from the repository root:

cargo metadata --locked --format-version 1 > /tmp/xgpui-metadata.json
cargo run --locked --manifest-path tools/release-sync/Cargo.toml -- check-local-dependencies --metadata /tmp/xgpui-metadata.json

This checks local framework sources, pinned registry helpers, and accidental pulls of the upstream framework alongside the local fork.

Downstream release identities

scripts/release-packages.json defines downstream package identities and individual version overrides for ten framework/backend crates and seven extensions. Normalization applies those versions while keeping directory names, library names and dependency aliases stable. The helper package version follows the captured release/1.28.1 provenance independently. upstream.json records both sets.

For example, the local gpui crate is packaged as xgpui; applications retain use gpui::* through a Cargo alias. Internal dependencies use exact requirements from the release map. Supporting packages retain their upstream identities and =1.28.1 requirements. The selected downstream family uses core 4.0.0, Apple 5.0.0 and macOS 5.0.0, with matching pins. Interactive iOS simulator/device validation remains pending.

Website deployment

.github/workflows/pages.yml runs on manual dispatch only. It checks pages/, builds both demo collections, checks that the bundles exist and uploads pages/ as is. Internal documentation and tooling are never uploaded.

Select Settings → Pages → Source: GitHub Actions. After deployment, repeat the browser checks at https://xgpui.dev/ and refresh nested URLs directly to catch stale assets.
