GPUI public API changes

Breaking changes to XGPUI API

XGPUI extends GPUI through optional extension crates and a maintained set of core integration points. This page documents our changes to GPUI: font controls, color and rendering contracts, paragraph layout, and the backend interfaces needed by those extensions. Optional feature usage can still require changes to an application's core GPUI code when public structs, traits or resource handles change.

Check each compatibility section when upgrading. In particular, exhaustive font and style literals need new fields, and custom renderers or text backends must follow the documented ownership and backend contracts. Constructors and defaults preserve existing behavior where the individual section says they do.

The GPUI 1.27.0 migration and API review separately identifies upstream changes carried into XGPUI and adaptations to our existing APIs. That integration is awaiting final public API approval. Its upstream release reference links the original GPUI commits and pull requests.

The maintained XGPUI feature changes below are compared with pre-feature main 9b64657.

Font axes and inspection: core 3.0

xgpui 3.0.0 adds variable-font controls and resolved-face inspection. Native CoreText, DirectWrite and Parley share the same contracts. See variable fonts and OpenType inspection for examples and the release versions for matching pins.

GPUI 1.26.2 migration

The update merged after the October 31 release moves the core to xgpui 2.0.0 while preserving XGPUI’s objc2/objc2-metal integration. The registry versions are published; use matching core, backend and extension versions when upgrading.

  • Replace PlatformInput::ScrollWheel with Scroll and handle BackGesture in exhaustive matches. ScrollWheelEvent and on_scroll_wheel remain deprecated compatibility names; new code uses ScrollEvent and on_scroll.
  • Complete ScrollEvent literals need source; WindowOptions and WindowParams gain use_display_p3; WindowInsets gains corner_radii.
  • Construct Metal contexts with MetalCustomContext::new. Producers use record() and finish all encoders inside its closure; only the host submits. Use queue_identity() for cache identity. Context struct literals and public queue access are no longer supported. Resource handles remain objc2 types.
  • Custom integrations that mirror GPU sprite layouts need the updated field ordering used by the Rust, WGSL and HLSL definitions.

See What’s new for features and the reviewed version family.

Application examples · Preparation and failure contracts

ADDED SVG viewport size

Required by: xgpui-svg.

ParsedSvg::size() -> Size<f32> returns the resolved document viewport in SVG user units. The extension uses it for aspect-preserving sizing without parsing the document a second time. Existing parsing/rasterization signatures remain unchanged. SvgImage, policy, scheduler, atlas lifetime handling and aggregate image accounting live in the extension and depend on existing GPUI element, executor, state and image APIs.

ADDED SVG viewport rasterization

SvgSize::Viewport { size: Size<DevicePixels>, view_box: Bounds<f32> } lets SvgRenderer::render_parsed rasterize a visible rectangle in resolved document coordinates into an exact output. The browser comparison uses this to keep curves sharp while zooming without growing the whole-document output. It retains the parsed tree and caches unchanged camera/viewport output in the demo.

Each output edge must be 1..=8192; invalid, nonfinite or nonpositive rectangles return InvalidSize. Existing sizing modes retain their behavior. Adding an enum variant requires downstream exhaustive SvgSize matches to handle it. This output bounds the destination buffer, not resvg filter intermediates or whole-process memory. It does not add cropped scheduling to SvgImage or make browser rasterization run on a worker.

Experimental instanced shader additions

Scene::shader_draws, Primitive::Shader, PrimitiveBatch::Shaders, SceneShaderProgram, ShaderDraw and Window::paint_shader support the instanced shader extension. Exhaustive scene literals and enum matches must accommodate these additions. Ordinary styled elements retain their existing call sites. Programs and backend pipeline ownership are separate: the extension validates/translates sources, and each host renderer creates pipelines on its own device.

Explicit instanced shader output encoding

ShaderOutputEncoding is a new non-exhaustive enum with EncodedSrgb and LinearDisplayP3. SceneShaderProgram::new retains its signature and sRGB behavior; additive new_with_output_encoding and output_encoding methods allow extension compilers to declare immutable output meaning. Its fields remain private. A wide program's generated wrapper must follow the host color/alpha contract; metadata alone does not transform arbitrary user shader source.

MetalHeadlessRenderer::set_color_mode (macOS) and Dx11HeadlessRenderer::set_color_mode are additive test-support APIs for native offscreen validation. Window APIs and existing scene/primitive layouts are unchanged by this addition.

ADDED source-sized media textures

ImageTextureData validates an immutable complete RGBA8 ↗ mip chain ↗ within 64 MiB and bounded dimensions. Backend create_image_output methods record uploads without submitting or waiting. Metal uses a distinct MetalImageOutput type; wgpu/D3D11 outputs carry a private source-sized tag set only by these constructors. Their old create_output methods still validate exact raster extents.

The shared custom compositor uses trilinear image sampling ↗; single-level producer textures retain their previous filtering behavior. No existing public method signature or public scene-record layout changes in this addition. Decoding, mip generation, admission policy and image elements belong to xgpui-media. See its resource and color contracts.

Worker staging handoff

The media extension now stages full images on bounded native workers. Metal's stage_image_upload owns a worker autorelease pool. wgpu/D3D11 contexts expose owned image_upload_context handles with stage; their opaque staged-image types are bound to the original host queue/context and accepted by adopt_image_upload. Adoption records copy commands without allocating or copying the source pixels. Output is_submitted distinguishes host acceptance from pending/abandoned work; GPU completion remains a separate concern. Existing context layouts, recording transactions and synchronous image constructors remain compatible.

Window::element_opacity() is now a public read-only getter (previously crate-visible). Media painting combines it with bounds/content-mask checks to avoid requesting loading frames for empty, fully clipped or zero-opacity content. Its calculation and element-drawing-only contract are unchanged. Window::with_element_opacity is also public so external custom elements can multiply their own style opacity into that inherited value while painting or prepainting. The media viewport uses it to apply its opacity style exactly once.

Completion-safe staging pools and scene-frame admission

ImageStagingPool, ImageStagingLease and their counters provide bounded resource reuse for backend SPI. Metal/wgpu opaque staging pools retain exclusive leases through GPU completion; wgpu recording transactions drop unsubmitted guards when abandoned. The D3D11 staging path remains unpooled pending native validation.

PreparationFrame shares loader-keyed count/byte counters for one scene preparation. CustomContent::prepare_in_frame is an optional trait method whose default calls prepare_with_request; old producers need no changes. Window preparation adapters forward the frame alongside original logical geometry. Media's policy and defaults live in xgpui-media, not in GPUI's renderer types.

Custom-content image color transforms

CustomContent::image_color_transform() is a defaulted method returning three encoded-sRGB affine RGB rows. Identity is the default, preserving existing implementations and outputs. The logical-geometry adapter forwards it. Compositors apply it after sampling/unassociation and before coverage and opacity, preserving alpha. Native wide-color background adapters retain their separate color contract. xgpui-media::ImageFilter, FilteredImage, MediaImage::filtered, MediaImage::paint_filtered and MediaImageView::filter expose ordered SDR ↗ color adjustments while sharing source texture uploads. Private compositor parameter blocks grow from four to seven float4 rows; backend context/output layouts and public scene record fields are unchanged.

Contour path effects

xgpui-svg::path_effects adds Contour, Segment, MeasuredPath and PathEffect. The measurement cache retains Bézier curves and supports total-length trim plus per-contour dash phase before native stroke tessellation. This adds no core GPUI API or scene-layout changes; existing PathBuilder and SVG raster APIs retain their behavior. Measurement and effect fragmentation have explicit work limits.

Native video snapshots and bounded presentation

xgpui-media adds VideoFrame, VideoStream, VideoSender, VideoStats, VideoView, video and video_frame. These are additive APIs; existing image loaders and scene records are unchanged. The macOS re-export CoreVideoFrame provides a checked BGRA/IOSurface import with an unsafe external synchronization and immutability contract. Source-sized Metal outputs now accept BGRA8 ↗ as well as RGBA8. The Metal compositor retains custom-content producers through sampling completion, allowing immutable external frames to outlive their source scenes.

Legacy Metal PaintSurface rendering accepts BGRA plus the existing full-range NV12 ↗ format. Unsupported formats propagate errors and close active encoders; CoreVideo views/pixel buffers remain alive until GPU completion. This does not change public PaintSurface fields or Window::paint_surface signatures. This macOS slice supplies no decoder. Windows DXGI and Linux DMA-BUF adapters are described separately below; system playback remains separate issue #40.

Windows native BGRA snapshots

gpui_windows::custom_draw::dxgi::DxgiFrame imports dedicated immutable same-device BGRA8 D3D11 render targets for source-sized sampling; xgpui-media re-exports it and adds VideoFrame::dxgi. Construction is unsafe: callers synchronize producer writes and preserve immutability through the native resource lifetime. The adapter direct constructor rejects keyed mutexes and foreign devices. The separate unsafe try_from_shared_bgra constructor opens an NT handle on the host device and nonblockingly acquires a keyed read lease; clones/prepared outputs retain it until submission/discard, with the last reference handing ownership back to the producer. Timeout returns no frame; abandonment requires resource recreation. No decoder or playback API is added. Windows compilation is checked; native runtime verification is outstanding.

Linux Vulkan DMA-BUF snapshots

The opt-in gpui-wgpu/dma-buf module adds DmaBufLayout and DmaBufFrame; xgpui-media/wgpu re-exports them and adds VideoFrame::dma_buf. The initial unsafe adapter owns an FD for a dedicated immutable linear BGRA snapshot with producer synchronization already complete and EXTERNAL/GENERAL Vulkan ownership. Preparation imports the native allocation, records host queue acquisition and caches a source-sized output. Device capability is enabled only when advertised. No decoder, sync-file import, pool-recycle signal or foreign-family GBM/EGL import is provided. Linux compilation and host layout tests pass; native GPU validation is pending. See the media guide for exact layout and lifetime requirements.

macOS NV12 snapshots

CoreVideoFrame::from_nv12(buffer, Nv12Matrix) adds opaque 8-bit two-plane CoreVideo NV12 import to the existing styled video element. xgpui-media re-exports Nv12Matrix::{Bt601, Bt709}. Range is selected from the buffer's 420f / 420v format. Construction remains unsafe: producer synchronization, immutable pixels/attachments, matching SDR matrix and centered chroma are required.

Metal imports R8/RG8 plane views and samples/converts them in the existing custom compositor pass. Internal prepared output/uniform handling changes; public MetalCustomOutput fields and existing generic output contracts remain unchanged. Legacy PaintSurface behavior is preserved. No decoder, playback clock, transfer conversion or HDR ↗ support is added. All four range/matrix combinations have native release pixel/lifetime coverage and an interactive generated-source lab mode.

Synchronous mip-chain preparation

xgpui_media::mipmapped_rgba8(width, height, rgba) is an additive extension helper returning validated gpui::ImageTextureData. It uses the native loader's same alpha-aware linear-light area filtering, dimension and complete-payload bounds. It performs synchronous CPU work without loader reservations or worker scheduling; use it for small already-decoded fixtures or with a host-managed executor. The browser media examples use it with the existing wgpu image-output SPI; the native loader's threading contract is unchanged. Existing GPUI call sites are unaffected.

Media pipeline CPU contracts (issue #26 Phase 1)

xgpui_media::pipeline adds explicit SDR source/working color metadata, an alpha-preserving linear ColorMatrix and Vignette reference, progressive publication states with stale-result protection, tile identities/accounting and future scheduler budgets. These are extension APIs; this phase adds no GPUI renderer SPI or new GPU path. ImageFilter retains its encoded-sRGB contract.

PipelineCapabilities::current() reports the new GPU features as unsupported until their respective phases land. See media pipeline contracts for the public types, examples, validation and remaining implementation work.

Linear image sampling parameters (issue #26 Phase 2)

CustomContent::image_linear_adjustments is a default-None hook that forwards through preparation geometry wrappers. LinearImagePaint validates finite f32 matrix/vignette parameters for encoded-sRGB source images. Metal, wgpu and D3D11 carry those per-placement parameters separately from retained source resources; the existing image_color_transform method keeps its encoded-sRGB behavior. The linear hook replaces it when present. The private compositor uniform ABI expands consistently in Rust, MSL, WGSL and HLSL.

The extension exposes pipeline::ImageAdjustments, AdjustedImage, MediaImage::adjusted/paint_adjusted and MediaImageView::adjustments. The last filter/adjustments setter selects the interpretation explicitly. P3 working matrices and unsafe f32 conversions are rejected by the rendered path.

Phase 3 source texture color support

ImageTextureData::new_linear_p3_rgba16f validates full premultiplied ↗, bounded linear-P3 binary16 ↗ mip chains. format() and bytes_per_pixel() drive upload size/format on Metal, wgpu and D3D11; staging accounting includes the 8-byte pixel size. CustomContent::image_color_mode defaults to the old encoded-sRGB interpretation; float preview/wide modes are explicit. LinearImagePaint::with_p3 declares P3 working primaries.

The native wide placement uses the existing wide-SDR compositor and requires window opt-in. wgpu rejects wide placement; it offers an explicit sRGB preview. Core source metadata must match the GPU texture format. Existing producers keep their default hooks. See media pipeline for examples and limits.

Phase 4 tiled preparation and lifetime support

ImageTextureData::page validates a single immutable mip page. Existing constructors still require complete whole-image mip chains. CustomContent::image_source_size declares source-sized preparation independently of a large virtual destination; geometry remains finite and clipped normally. image_sample_opacity separates preparation from sampling visibility, allowing a page to warm up before replacing its progressive fallback. Defaults preserve existing producers.

wgpu retains source snapshots until queue completion; D3D11 event queries retire them after sampling. Metal already retains them through command completion. Media payload guards also follow upload completion. These lifetimes let tile budget leases count evicted but still-used resources. Per-frame image transfer accounting now charges aligned staging bytes instead of only unpadded payload. See progressive tiled canvas for examples and QA limits.

Phase 5 effect reuse

xgpui_shader::LayerEffect::paint is public for bounded paint closures. xgpui_media::pipeline::ImageBlur validates the existing layer capture/support limits and reuses that compositor rather than adding another blur engine. Assembled tiled previews share one kernel across page edges. This path filters premultiplied encoded sRGB and does not provide wide-SDR or source-space blur. VideoFrame::adjusted and VideoView::adjustments forward immutable native preparation/ownership with linear placement uniforms; VideoView::blur uses the same bounded preview path. See the media pipeline guide for errors, fallbacks, separate effect memory and runtime QA limits. No core ABI change was needed.

Canvas reuses existing GPUI APIs

The xgpui-canvas crate uses existing containers, content masks and the xgpui-shader instanced pipeline. It adds no GPUI public signatures or fields. Its own camera, scene, pan and grid APIs are experimental; callers project children explicitly and own application input/selection policy.

Supplied pixels, custom RGB and native color checks

Start with color tasks for practical integration. PixelColor distinguishes named ImageColor, custom RgbDefinition and extended-linear source samples. MediaLoader::load_pixel_buffer accepts that resolved interpretation, an explicit storage space and a mapping policy. Storage can be bounded P3 or Rec.2020 RGBA16F; native-wide placement converts it into the compositor's extended coordinates.

RgbDefinition supports reference-white adaptation and independent channel curves. from_relative_xyz_matrix preserves relative colorants whose sum differs from the declared XYZ reference white. The optional xgpui-color/icc parser constructs definitions from a bounded RGB matrix/TRC subset; it does not add image-file decoding or a general ICC transform engine. See pixels + metadata and ICC scope.

The Metal test-support API Window::render_to_linear_p3 reads FP16 composition values before OS display mapping. The ordinary 8-bit screenshot remains an sRGB preview. Color labs separates CPU conversion, GPU composition, browser preview and physical display claims.

Engine surfaces from independent GPU engines (#197)

Added for the experimental xgpui-surface extension and approved in the #197 API review (2026-11-11). The hooks ship in xgpui-wgpu 2.3.0, xgpui-windows 2.2.0 and xgpui-apple 4.1.0. An engine keeps its own GPU device and presents frames into xgpui through a ring of shareable slots. The surface, ring, sync points and engine adapters live in the extension. The macOS ring uses the existing MetalCustomOutput, MetalWideSdrOutput and MetalCustomContext::record; only the non-wide RGBA16F preview (K2) needs a Metal addition. The additions below are what the extension cannot do from outside gpui-wgpu and gpui-windows. Evidence and transport details: issue #198 (spikes) and PRs #200–#204.

Two internal behaviour changes add no API:

  • D3D11 retirement: the renderer now retires each frame's custom-content snapshots through a D3D11.4 fence and a worker thread, instead of only through event queries read during later frames. Snapshots are released once GPU sampling completes, even if no later frame is drawn. Event queries remain the fallback, and GPUI_D3D11_FENCE_RETIREMENT=0 forces them as a diagnostic. Snapshot Drop can now run on that worker thread, as it already can on Metal's completion threads; CustomContent is already Send + Sync.
  • External-memory device: the Linux device-creation path changes only with the external-memory feature (first row).

None of these changes an existing signature, serialized format or default behaviour, and no existing application needs to migrate.

Tests: Linux and Windows runtime tests on an Intel Iris Xe laptop cover exact pixels, wide/preview colour, snapshot immutability, ring cycling, cross-thread presentation, gated GPU-side waits (about 302 ms held), idle release and clean exit. macOS tests cover the Metal path. Real-window labs hold 60 fps (p95 about 17 ms) on all three platforms.

GPU device-loss reporting (#119)

Approved in the #119 API review (2026-11-12) for core 3.2.0. When the GPU device is lost and recovery gives up, windows stop drawing and the application is told once, instead of Windows panicking or Linux retrying every frame forever. Input, timers and the rest of the application keep running, so the application can save state and tell the user.

Core additionPurposeCompatibility and migrationWhy core
GpuDeviceLost { reason }Describes the failure; reason is the backend's last recovery error, for logs and bug reportsNew #[non_exhaustive] struct with GpuDeviceLost::new; no serialization implementationShared by backends and the application
Platform::on_gpu_device_lost(...)Main-thread notification from the backendDefault no-op preserves platform implementersDevice recovery runs inside the backends
App::on_gpu_device_lost(...)Scoped subscriptionAdditive; retain the Subscription to observe, drop to stop; applications that don't subscribe are unaffectedApp observer lifecycle

Behaviour by backend:

  • Windows: the device is still recreated up to 5 times. If that fails, or a window cannot use the recovered device, every window stops drawing and the application is told; this replaces two panic!("Device lost") calls.
  • Linux (X11 and Wayland): a window retries recovery up to 5 times, waiting 100 ms after the first failure and doubling each time (about 1.5 s in all), then stops drawing and the application is told. A successful recovery resets the count.
  • macOS: not reported. xgpui never selects a removable Metal device, and only removable devices are removed; Metal command-buffer errors are per-buffer GPU resets, after which the device keeps working.
  • Browser: out of scope; the existing reload message stays.

After a successful recovery, xgpui rebuilds its own GPU state: atlases, glyphs, paths, shaders and built-in paints. Custom content is prepared again on the new device, so a producer that caches GPU outputs must check can_reuse (on the wgpu and D3D11 preparation contexts) and recreate them. xgpui-surface re-imports its slots on the new device by itself; only a loss of the engine's own device needs a new surface.

Hardware test runs: debug and test-support builds of the Windows and Linux backends read two internal environment variables, which release builds compile out. XGPUI_FAULT_GPU_LOSS_AFTER=<seconds> reports a device loss after that delay, and XGPUI_FAULT_GPU_RECOVERY=fail makes every recovery attempt fail. They are not API.

None of these additions changes an existing signature, serialized format or default behaviour, and no existing application needs to migrate.
