Shell lab and Linux preferences

Interactive diagnostics for xgpui issue 149. The lab reads the platform's current preferences and uses the same ShellOptions::resolved_preferences resolver as the client frame. It never writes desktop settings.

Run

From the xgpui repository:

just profile=dev lab-shell

# Ask for the xgpui client frame on Linux (the compositor can decline).
just profile=dev lab-shell --client-decorations

# Exercise a non-resizable window.
just profile=dev lab-shell --client-decorations --fixed-size

The shell is experimental. This release prepares its first crates.io publication; repository builds use the local workspace crate. The first build uses the existing native extension-lab workspace and its dependencies.

What to inspect

  • Detected: actual values exposed by the platform snapshot. Missing values say not reported; this can mean an absent setting/provider, an unsupported platform, or an initial snapshot still pending. The API does not currently distinguish those cases, so the lab does not claim a specific reason.
  • Resolved client frame: actual resolver output after this window's overrides, desktop preferences and built-in fallbacks. Native/server decorations retain control of their own appearance; resolved values do not prove the compositor is displaying xgpui's frame.
  • System / explicit override: selected buttons show each window's current override. Explicit Normal, Black and None are preserved; Reset clears every override for this window only.
  • Typography / reduced motion: common desktop font descriptions now style the client-frame title. Per-window typography and motion-policy overrides are available. Motion is a resolved policy only: this static frame has no animations.
  • Window state: requested and platform-reported decoration modes, appearance, button layout, activation, maximization/fullscreen, capabilities, bounds, viewport and device scale. Decoration requests may be declined or arrive asynchronously; inspect the reported result.
  • Recent events: the last twelve distinct notifications/actions, newest first. Refresh View only rereads displayed state; it does not force a portal request.

All interactive buttons support pointer activation, Tab focus, Enter/Space and accessible click actions. Unsupported operations are dimmed and do not dispatch.

Client-frame preview on Mac (or any host)

The left pane contains a clearly labeled simulation, using the same renderer as the production client frame. The right pane scrolls independently, keeping the preview visible while changing per-window overrides.

  • Change contrast, accent, typography and logical scale in the right pane to inspect their rendered result. Show Focus Ring simulates focus on the decorative close icon so accent changes remain visible without making preview controls actionable. Show Hover independently simulates the close-button hover background.
  • Select Floating, Maximized, Tiled or Fullscreen, Light/Dark/native appearance, Active/Inactive, and alternate button layouts in the preview controls.
  • Toggle the long title in Window Operations to inspect truncation in the preview.
  • Preview buttons are decorative images; clicks, double-clicks, drag regions and resize borders do not close, move, resize or change the host window. Use the separate native Window Operations controls to operate the real window.
  • Simulated choices are never stored in the detected platform snapshot. They do not claim to validate Linux compositor behavior or real desktop integration.

Window Menu and decoration requests are disabled on macOS/Windows, where the current backend operations are no-ops. Dispatch guards enforce the same rule as the buttons, even if an unsupported action is invoked programmatically. The Linux-only --client-decorations startup option is ignored on these platforms.

Manual Linux check

  1. Start the client-decorated lab on Fedora GNOME or Ubuntu GNOME. Confirm the reported decoration mode before judging frame styling.
  2. Change appearance, accent, contrast, text scale, button placement and title-bar actions through the desktop settings UI. Watch detected values and events. Portal values take precedence; optional GNOME/KDE native fallbacks fill missing preferences. See provider coverage.
  3. Override contrast, accent, typography, scale and click actions in this window. Check that the client frame responds and desktop settings remain unchanged. Click the real title bar to exercise its selected action.
  4. Open a second window. Verify independent defaults and titles; reset one window while leaving the other's overrides intact.
  5. Try maximize/restore, fullscreen/exit, window menu, compact/normal size, the long title, and drag/resize. Minimize is restored through the desktop. Use desktop snap/tiling gestures to test tiling; the lab does not invent a portable tiling API.
  6. Open a fixed-size window and verify resize/maximize controls are unavailable.
  7. Move windows between displays and inspect device scale separately from logical text scale. Repeat with server decorations and another desktop/compositor.

On macOS, native traffic lights remain while the app composes the title/app bar. On Windows, this composition path uses custom title-bar content and shell controls. Overrides style the app bar and simulated frame; they do not change native macOS traffic-light artwork. No behavior is selected from the displayed distro name.

How the look is applied

The new left-pane inspector uses ResolvedShellPreferences::resolved_look, the same resolver consumed by the production client frame and its safe preview. It displays the exact header, text, border, hover and effective focus colors; requested title font family/weight/style, scaled logical size, header height and button target size; and the resolved click actions and reduced-motion policy.

  1. Choose typography and logical scale in the right pane. The title changes; the sample body and lab controls keep their independent styles.
  2. Select Light/Dark and Active/Inactive. Compare the displayed color swatches with the header and title. Contrast selects the accessibility palette.
  3. Choose an accent and toggle Show Focus Ring. In high contrast, focus uses the foreground color instead of the accent. Toggle Show Hover to inspect its background independently; both can be visible together.
  4. Toggle reduced-motion policy. The inspector shows the resolved policy without pretending there is an animation to disable. Current hover/focus changes are instant.
  5. Reset this window. Desktop values or built-in fallbacks return. Open another window to check independent settings. Actual pointer/keyboard behavior on a native Linux client frame remains part of final platform validation.

Fonts are requested, not reported as actual matched faces. GPUI may substitute an installed family or fall back for particular glyphs. The close icon is a vector; other control symbols use stable system typography independently of the title. Native/server decorations retain OS-controlled typography and colors; the app-owned bar inside or alongside them can use the shell look or app-supplied styles.

Typography contract and limits

ShellTypography { font: gpui::Font, size: f32 } is an extension API for explicit client-frame typography. ShellOptions::typography overrides the desktop font; None parses a desktop description or falls back to system UI at 14 logical px. Size is bounded to 8–48 before text scale (0.5–4), and the header grows to contain larger titles. Points convert at 96/72 logical px; device DPI is applied later by the renderer, never multiplied into this value again.

The parser supports common Pango family/size/weight/style descriptions, including px and comma-terminated family names, and the family/size/weight/style subset of Qt 5/6 QFont strings. It is intentionally not a complete Pango/Qt interpreter: Pango family lists, stretch, variants, features and variation syntax are unsupported; QFont attributes beyond family/size/weight/style are not applied. Unsupported or invalid descriptions fall back; the raw description remains visible. Explicit gpui::Font overrides can supply features/fallbacks/variations directly.

Format references: Pango descriptions and QFont serialization.

App-composed title/app bar

The real window's top bar, above the lab panels, now demonstrates the shell-2026 composition model. The app supplies SVG artwork, controls, title and spacing. No icon-theme catalog or layout presets are added.

  • Reset icon: clear this window's overrides.
  • Panel icon: hide/show the raw platform preference panel.
  • Title/empty space: explicit drag surface, separated from app buttons.
  • Theme icon: toggle the simulated preview's appearance (not desktop settings).
  • Plus icon: open an independent lab window.

On macOS, the real native traffic lights remain at the left, with reserved space; the app bar fills the transparent title area. On Windows the app-composed bar uses the shell's window controls and native hit-test regions. On Linux a negotiated client frame wraps the app bar with window controls and resize edges. If the compositor supplies server decorations, the app bar sits inside the native frame and does not duplicate window controls. In fullscreen the app bar remains useful while window controls and native traffic-light clearance are omitted.

The separate client-frame preview still shows built-in frame defaults; it is not a clone of the actionable app toolbar. Its decorative buttons remain inert.

Developer entry point

Use ShellApp::open_shell_window_with_titlebar instead of open_shell_window:

cx.open_shell_window_with_titlebar(
    window_options,
    ShellOptions::default(),
    |window, cx| {
        let header = cx.new(|cx| MyHeader::new(window, cx));
        let content = cx.new(|cx| MyContent::new(window, cx));
        (header, content)
    },
)?;

MyHeader is an ordinary GPUI Render entity. Luma can supply its own SDK controls, look, icons and layout there. The shell wraps that content with its default background/typography and platform controls; child elements can supply their own styles. Use ShellDragRegion::new(id, content) for title text/empty drag surfaces, and keep interactive controls as siblings. A drag begins after a four-logical-pixel threshold; release clears tracking. Default macOS double click delegates to the native preference. .options(...) on the region can provide the window's explicit action overrides. Windows delegates dragging/control hit tests to the native path.

The original open_shell_window API is unchanged and still uses default chrome. The new method configures transparent/custom title-bar options on macOS/Windows; macOS traffic lights are positioned for the resolved header height. Apps that need further native positioning can use existing GPUI window APIs from their header. Linux decoration requests continue to be negotiated with the compositor.

This is an extension-only addition (ShellApp method and ShellDragRegion); no new core GPUI public API or serialization changes. Implementers of the experimental ShellApp trait need the new method; application callers using the existing method need no changes. Prerequisite #182 core API review remains separate.

Linux desktop preferences

The shell work is integrated. This release prepares the first shell publication; final core API release approval and native desktop acceptance remain separate gates.

Integration

App::desktop_preferences() returns optional platform values. App::observe_desktop_preferences(...) reports changes; keep the returned subscription alive. The shell subscribes once per shell entity and redraws that entity when the desktop snapshot changes. Applications do not need a D-Bus client.

ShellOptions::default() follows the available desktop values. An explicit Some(...) overrides the corresponding value, including Some(false), Some(0) for a black accent and Some(TitlebarAction::None) for disabled actions. ShellWindow::set_options replaces the window's overrides and redraws it.

The existing light/dark and button-layout APIs remain responsible for those preferences. Other platforms currently return an empty desktop snapshot; their native window chrome is unchanged.

Providers and fallbacks

Values resolve per field: standardized portal value, desktop portal extension, optional native desktop reader, then the consumer's default. Explicit window options continue to override that result. False, black and TitlebarAction::None are values, not missing settings.

The native reader is selected by colon-separated XDG_CURRENT_DESKTOP tokens: GNOME/Unity (including ubuntu:GNOME) or KDE. Other desktops use the portal and consumer defaults. Merely installing GNOME schemas on KDE does not activate the GNOME native reader. KDE/GNOME portal extensions remain optional; they are not freedesktop standards.

GNOME uses three concurrent, read-only gsettings list-recursively schema reads. KDE uses concurrent kreadconfig6 queries, with kreadconfig5 as an optional fallback, for kdeglobals font/animation preferences and KWin title-bar actions. KConfig handles config search paths, escaping and inheritance; the toolkit does not parse private INI files. No command uses a shell or writes preferences. Commands run in the background with five-second deadlines and kill-on-drop; missing tools, denied sandbox access, invalid values and failed queries leave individual preferences unavailable. Applications need no command or D-Bus code.

The portal subscribes before reading, deduplicates across reconnects, refreshes every 15 seconds and retries failed sessions after five seconds. Native results are cached for 15 seconds during a healthy portal session, so portal signals do not launch commands repeatedly. During outages native preferences are still read on retries. Appearance/layout/cursor values retain their last-known values only when the failing portal and native reader cannot supply them. Extra optional preferences clear when unavailable. Successful empty snapshots reveal native fallbacks or restore consumer defaults. Explicit window overrides survive both.

KDE font descriptions retain QFont serialization; GNOME descriptions retain Pango syntax. Neither is a family name. KDE display DPI is deliberately not converted to logical text scale (that would risk double scaling). Unsupported KWin actions, such as shading or vertical-only maximization, remain unavailable. KDE native button-layout, palette and cursor config are not guessed; their existing portal or consumer defaults apply. No app-wide fonts, animations or theme are changed.

Experimental shell migration

The earlier local-only shell's scalar options are now optional overrides. Replace high_contrast: true with high_contrast: Some(true), and similarly wrap explicit accent, scale and double-click values. New middle/right-click override fields can be omitted with ..Default::default(). Callers already using ShellOptions::default() need no source change. Local lab adapters use that default constructor.
